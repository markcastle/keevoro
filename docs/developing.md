# Developing Keevoro

Everything you need to build it from source, test it, and cut a release. For why the code is shaped the way it is, read [PLANNING.md](../PLANNING.md); for the rules every change must follow, read [AI_AGENT_PROMPT.md](../AI_AGENT_PROMPT.md).

## Building and testing

You need [Rust](https://rustup.rs). The repository pins the stable channel in `rust-toolchain.toml`, so `rustup` picks the right one. If CI complains about something your machine accepts, your stable is probably older than GitHub's:

```sh
rustup update stable
```

The four commands that must pass before a pull request:

```sh
cargo fmt --all
```

```sh
cargo clippy --workspace --all-targets -- -D warnings
```

```sh
cargo test --workspace
```

```sh
cargo run -p keevoro-cli -- survey <a folder of photos>
```

CI runs the same on Windows, macOS and Linux, and fails if fewer than 90% of lines are covered by tests.

### The desktop app

The app is four layers, and almost all the thinking is in the bottom two:

| Layer | Where | What it is |
| --- | --- | --- |
| Screens | `ui/src` | React and TypeScript. They show what they are given and send one request per button. |
| Shell | `src-tauri/src` | A Tauri window and a handful of commands. Each command finds the open backup, calls the API, and turns an error into a sentence. Long jobs are the API's; what they say reaches the window through one listener set up in `lib.rs`. |
| API | `crates/keevoro-api` | Every operation Keevoro offers, listed once in a register. What the app, the command line and an AI agent all call. See [The API](#the-api) below. |
| Engine | `crates/keevoro-engine` | Everything Keevoro actually does: the Discover view, choosing, previews, backing up and connecting storage. Tested without a window. |

If you are about to write a rule about photos in the shell or the screens, it belongs in the API or the engine instead.

```sh
npm install
```

```sh
npm run dev
```

That builds the screens, starts the shell and reloads as you edit. On Linux the shell needs a few system libraries first: `libwebkit2gtk-4.1-dev libgtk-3-dev librsvg2-dev libayatana-appindicator3-dev`.

The screens can also run alone in a browser, which is the quickest way to work on how things look:

```sh
npm run ui:dev
```

There they talk to a stand-in for the engine (`ui/src/demo.ts`) with drawn pictures, so no drive or backup is needed. Add `?closing` to see what is said the first time the window is closed, `?quitting&busy` for the question before quitting cuts a backup short, `?demo=new` to see the first-run screen, `?demo=empty` for a backup with nothing found yet, or `?demo=scans` for a new backup holding a folder of family scans, not yet asked how to arrange it. `?page=settings/byItself` opens on a page, as the icon by the clock does.

The app updates itself through `src-tauri/src/updates.rs`, which leans on `keevoro-update`: the same "find the latest release, download, compare with SHA256SUMS" rules the command line uses, applied to the installer. Installing closes the app on Windows, so it never starts while this app has a search, a backup or a check in hand (`updates::may_install`, pure): `install_update` answers `waiting` instead, the window asks again every five seconds, and "Stop it and update now" stops the work after the file in hand first. To see the offer in a browser, add `?update` to the address, and `&busy` to see it wait.

Searching is split in two. The search itself (`keevoro-scan` with `quick: true`) only samples large files and marks them `hashed: false`. `keevoro-engine/src/deep.rs` then reads those files whole, in the background. The rule that must never be broken: nothing is dropped as a duplicate on the strength of a quick fingerprint, and no copy counts until it is proved exact against the whole file. Before reading anything, the check looks once at each source with the one rule for "plugged in" that a search, looking again and a backup use (`keevoro_engine::reach::is_there`), and passes over every file of a source that is not there; a read that fails is followed by one more look at its source, and if it has gone the rest of it is passed over too, never tried file by file (`DeepReport::gone`). Those files stay not checked, and the check says what waits for which source (`words::check_waits_for`, in its last word, the log and `DuplicatesLeft`), ends when nothing else is left, and refuses "Check for duplicates now" with the same sentence when everything left is on sources not plugged in. The tests are in `deep.rs` (a source gone before and part-way through, and a healthy check looking once per source), `the_check_for_duplicates_waits_for_a_source_that_is_not_plugged_in_and_says_so` in `keevoro-api/src/jobs/tests.rs` and the app's wiring test.

A backup that goes straight to a destination does not read everything first, because that would read each file twice: once to fingerprint it and once to copy it. Before sending, it reads in full only the files whose quick fingerprint is shared with another file, since those have to be told apart (a true copy is left out, a lookalike is not). Every other sampled file is given its place under its quick fingerprint and marked `learn_fingerprint` on its `Upload`. The store or the uploader then works out the whole fingerprint in the same pass that sends it, the answer comes back in `PublishReport::learned`, and `Catalog::set_whole_hash` moves the file, its keep choice and its place over to the real fingerprint. A file that looks like another but cannot be read in full is given no place at all (`check_and_place` in `keevoro-engine/src/lib.rs`), so it is neither sent nor left out until it can be told apart.

Every write to a folder goes through Keevoro's working folder there, `.keevoro-uploads`, before it takes its real name. A copy that is stopped, crashes, is killed or loses its drive part-way leaves a `tmp-…` file there, and versions before 0.22 sent large files to folders in parts, leaving a folder of `part-…` files and a `target`. None of it can ever be carried on (a part-copied file is copied afresh, and folders are no longer sent in parts), so `sweep_working_files` in `keevoro-storage-folder` clears whatever has not been written to for an hour (`ABANDONED_AFTER`) and the working folder itself once empty. The hour is what keeps a live copy safe when another program, or another computer, backs up to the same folder at the same moment: a copy in progress writes every few seconds. It only ever removes Keevoro's own `tmp-…` files and hexadecimal upload folders inside that working folder, checks every path by where it really leads, never follows a link, and leaves anything it does not recognise. A backup sweeps each folder destination as its turn starts and ends (`send::tidy`), and says so in its summary and history when it freed 10 MB or more; taking a folder off a backup sweeps it too, and `destinations.tidy` (`keevoro tidy FOLDER`, and in the app the "Clear unfinished copies…" button beside a folder destination and "Unfinished copies in a folder" in Settings, Advanced, in `ui/src/tidy.tsx`) does it for any folder. With `dryRun` it only says what it would clear (`working_files_to_clear`, the same rules without removing anything), which is what the app asks first; what is left is counted by why (`in_use`, `not_ours`), and the sentences come from `keevoro_api::words::tidied`, so the app and the command line say the same. For cloud storage, an upload in parts this backup started for a file it no longer sends is aborted at the end of the pass (`abandon_unfinished` in `send.rs`), from the uploads the catalog remembers; one still being sent is kept and carried on next time.

A copy to a folder is proved in `Copy::store` in `keevoro-storage-folder`: the source is fingerprinted as it is read, and a file that is not the fingerprint expected is refused; the copy goes to a working file, is flushed to the disk or the far end, and takes its real name without ever replacing a file (a hard link, or a check and a move where there are none); then, at that real name, its size is asked afresh and it is opened afresh and read back in full, and it counts only if that is the full size and the same fingerprint. The proof comes after the last write and the move because on a network share that drops out and comes back the move can leave a file short or absent while seeming to work, which is how an owner's backup to a share came to record files that a later look could not find. Any error at any step is a failure, and nothing is recorded; a copy found wrong at its real name is left there (nothing in a backup is deleted) and is found and said by the next backup. Each problem carries the step it came at (`keevoro_storage::Step`: reading the source, writing, flushing, moving into place, reading back), so it is never said as the source's when it was the destination's. The few file operations are behind `keevoro_storage_folder::Files`, so `src/dropping.rs` can stand in a share that drops out at each step and show none of them is counted. Copying 600 MB of photos to a local disk in a debug build took 1.73 to 1.88 seconds before and after (`how_long_copying_200_photos_takes`, run by hand): the same one read back, made later. On a share it costs nothing more either, though a read back can be answered from the computer's own memory of what it wrote, so only a later look or "Check they all arrived", from a fresh connection, is the last word. It keeps the original's modified time. What `publish` records is the size that arrived (`PutReceipt::bytes`), the size a look compares with. A file already there under the same name counts only if it is the same size and, for a store that can read its own files, the same fingerprint (`same_or_refuse` in `keevoro-publish`).

### When a file cannot be sent, and a place that goes away

A long backup to a network share once said one line per file of "Couldn't read it from its source (The media is write protected. (os error 19))" and "(...account is currently disabled. (os error 1331))". The source was fine: Windows says those things when a share's session drops part-way. So:

- **Each problem carries its side.** `keevoro_storage::Step` (reading the source, writing, flushing, moving into place, reading back) on `StorageError::At`, and `keevoro_publish::cause_of` gives every failure a `Side` and a `Cause` (`keevoro_core::trouble`). Operating-system codes go through one pure table, `trouble::cause_of_code`, for Windows, Linux and a Mac, tested on every computer: on a network path, during a run that had already sent something, 19, 1326, 1327, 1330, 1331 (and a read-only file system or a plain input/output error on Linux and a Mac) mean the connection was lost; 51, 53, 55, 59, 64, 67, 121, 1222, 1231, 1232, 1236 and 2250 always do. A destination that says "not found" part-way through a run that was working has gone away, since Keevoro makes the folders it writes into. The raw text and code are kept in brackets in each file's reason in the history.
- **Said in groups.** `summary::failure_groups` makes one sentence per side and cause, largest first, with a count, the first three names and "and N more" (`trouble::group_words`): "Couldn't back up 132 files, because the connection to the folder Z:\Photos was lost for a while: IMG_0412.JPG, IMG_0413.JPG, IMG_0414.JPG and 129 more." The same sentences are the summary in the app, the command line and an agent's, and the stage's red mark says the largest group's short form. Every file is named, with its reason, in the backup's history (fifty by name, the rest counted). What failed is remembered for each destination (the catalog setting `not_sent:<target>`, at most 10,000 keys), so files that fail again are said as such ("These 12 files could not be backed up again, because..."). The last word carries `missed` and `checkAdvised`, so the main button says "Back up the 132 files that were missed" when that is all it will do, and "Check they all arrived" is the main button after a backup during which a place's connection was lost (`summary::check_advised_words`).
- **Retried at the end, never on the spot.** A whole file is never waited on and tried again where it failed (the owner's instruction: it wastes time while a share is away). One that fails for a cause that may pass (`Cause::may_pass`: the connection, a file in use, a copy that did not read back the same, an unknown problem) goes on a list, the run carries on with everything else, and at the end of the pass each is tried once more in order (`PublishReport::tried_again`). Parts of a large upload to cloud storage still have their few quick retries, since starting a large file again costs more.
- **A place that goes away.** The deciding rule is pure: `trouble::place_seems_gone` is true when the last `GIVE_UP_AFTER` (8) files all failed for a cause that may pass. Only then is the place asked, cheaply, whether it is there (`PublishOptions::reachable`: for a folder, whether it is still a folder). If not, no more files are started there in this pass: the run carries on with the other destinations; at the end it is asked once more, and if it is back the list and the rest are sent, and if not they are `waiting_for_place` and said ("The folder Z:\Photos went away part-way through and had not come back by the end, so 1,234 files were not sent..."). Nothing is sent into a folder that has gone, and the index is left for the next backup. A healthy run never asks (`a_healthy_run_never_asks_whether_the_place_is_there`). A source unplugged part-way is still said once for that source (`summary::source_unplugged`), in the same group of sentences.

The tests are `crates/keevoro-core/src/trouble.rs`, the place-gone and retry tests at the end of `crates/keevoro-publish/src/tests.rs` (with a store that goes away after five files and comes back, or does not), `crates/keevoro-storage-folder/src/dropping.rs`, and `crates/keevoro-engine/src/dropout_tests.rs`, which moves a destination folder away part-way through a real backup and runs the same files failing twice.

### Is it really there? Looking before counting

Keevoro remembers each file it sends to a destination (the catalog's `uploaded` table). It used to believe that memory, so a backup deleted from its folder was still said to be "already there", and a backup wrote the index and the note again without the photos. Our first outside tester found it. The rule now is that memory is corrected by looking, and everything that counts what is safe goes by the corrected memory:

- **One rule.** A file is at a destination when Keevoro sent it there and the last look found it there at the size it was sent: `Catalog::is_uploaded`, which reads the record's `gone` column (catalog step 9: `0` there, `1` missing, `2` not the size it was sent at). The plan of a backup, what is waiting and safe (`Reach::safe` in `discover.rs`, and so the Discover view, the room check, the rehearsal and the map's "Backed up: N of M"), what `publish` counts as "already there", and the index all ask it, so they cannot disagree.
- **How it looks.** `keevoro_engine::confirm` reads the records first, then lists `originals/` and `renditions/` at the destination by name and size (`ObjectStore::list_all`), compares them (`confirm::compare`, pure), and writes what changed back into the records with `Catalog::set_seen`. It never adds a record for a file it finds, so nothing someone else put there is taken for Keevoro's own, and it never changes anything at the destination. For a folder, `FolderStore::list_all` reads each folder's listing once, a level of the tree at a time, several folders at once across a network (`listing_at_once`, `reach::AT_ONCE_ACROSS_A_NETWORK`), never a file's contents; for cloud storage the default `list_all` goes through the store's own paged listing, never a request per file. Reading the records before the listing is what keeps a file another program finishes during the look from being taken for gone: a record is only written once its file is in place. A listing is not always the truth: on the owner's network share, after it had dropped out, one said 15 files had gone and 64 were another size, and every one was there and exact. So each record the listing would change to missing or another size is asked about on its own first (`confirm::recheck`, a fresh `head` of that one file), and that answer is what is written; a `head` that fails makes the whole look a failed look that changes nothing. Up to `RECHECK_AT_MOST` (2,000) are asked; past that the listing is believed for the rest only if it was right every time it was asked. On a made-up folder of 50,000 files a look takes about 0.2 seconds in a debug build (`how_long_a_look_at_50_000_files_takes`, run by hand), small beside telling apart and placing the same files before a backup.
- **When.** At the start of every backup (`send::everywhere`, before the plan, so the estimate counts what has gone) and every rehearsal, always; and when the backup screen opens (the app's `room` request, `Backup::room_looking`) or a destination is added, unless the last look is younger than `confirm::FRESH_FOR`, five minutes. Each look is kept as `looked:<target>` in the catalog's settings (`Looked`). What a screen is given (`LookedView` on each destination) says whether it is `fresh`; the app says "is there" only when every destination is (`ui/src/thereWords.ts`), and otherwise "was there when Keevoro last looked, 3 days ago".
- **What is said.** When a look finds originals gone, the sentence comes before anything is sent, in the rehearsal, on the backup screen and as the first lines of the backup: "The folder E:\Backup no longer holds 4 of the 40 files Keevoro backed up there. They will be sent again.", or, when Keevoro's note or index is gone too or most of it is, "looks emptied or replaced" (`confirm::looks_emptied`, `confirm::gone_words`). `publish` counts the files it sends whose record said gone (`PublishReport::restored`), and the backup says "Restored 40 files that had gone from there." and keeps the number in its history (`Sending::restored`). A file there at another size is never counted as safe and never replaced, since no original in a backup ever is; it is said, with what puts it right (`confirm::not_as_sent_words`). Each destination's originals pass ends with one sentence from `keevoro_publish::Account` (`summary::account_words`): every file given to the pass is exactly one of already there, sent, an exact copy left out, failed or not tried, which `every_file_given_ends_up_in_exactly_one_place_in_the_account_whatever_happens` checks over sixty made-up runs. The backup screen's line at the top (`ui/src/thereWords.ts`) says "N of your M files are safely there. K need attention." whenever a fresh look found any missing or another size, so it can never say everything is there beside them.
- **Out of reach is not empty.** A folder that is not there, a listing that fails part-way, or cloud storage that refuses the keys is a failed look: it changes no record, is said in the words a backup uses ("Keevoro can't find the folder E:\Backup. Is it plugged in?"), and a backup then does not go there. A folder destination is only ever made when it is added (`send::open_or_make`); `send::open` and `FolderStore::look_at` refuse one that has gone, because a backup folder that vanished is far more often a drive unplugged than a folder to make again on whatever disk is left.
- **Check they all arrived.** `send::check` reads each original back and writes what it found into the same records, so "Back up again to send anything that is missing" does exactly that.

- **Putting it right.** "Put this backup right" (`backup.put_right`, `keevoro repair`, `ui/src/putRight.tsx`, offered whenever the last look or check found any kept file missing or another size, and otherwise as a quiet "Prove every copy…" that opens the same plan) is `keevoro_engine::put_right`, one destination at a time, in a job that is a check to every other program (`JobKind::Check`, its own `op`, so no new word in the shared files) on a low-priority thread. What is known to be wrong is asked about first; then, unless `thorough` is false, every other copy is read back in full and compared with its original's fingerprint (`ObjectStore::holds_exactly`; a file only sampled is fingerprinted from its source, which is only read). A copy that is short, another size or not the same is asked about once more, then moved, never deleted or replaced, into `Set aside by Keevoro/<date>/` keeping its path (`keevoro_storage_folder::set_aside`: a hard link and the old name let go, or a check and a move; numbered if the name is taken; a note, `keevoro_core::SET_ASIDE_NOTE`, in that folder and the dated one). If the move fails the copy stays as it was and is said. Then what is missing is sent as a backup sends it, proved at its real name. Each copy proved is written down with when (catalog step 15, `proved_at`, `Catalog::set_proved`), every hundred files, and the setting `putting_right:<target>` keeps when this putting right began, so a stop, a crash or the share dropping out (five problems in a row with Keevoro's note no longer there, or any "not there" with the note gone, is out of reach, never missing, and nothing is sent to a folder that has gone) is carried on from without reading again what was proved; finished in full, the setting is set to `0`. The account (`put_right::Outcome`) puts every kept file in exactly one of proved, the right size (after a quick pass), or needing attention with why, and its words say "is right" only when every one was read back. Before it starts, `backup.put_right_plan` says what it will do and about how long, from the fastest turn the history recorded for that destination (`likely_rate`; else 8 MB a second across a network, 60 on a disk), with a quick first pass for what is known. In cloud storage a move is a copy and a delete, which Keevoro never does by itself, so a damaged copy there is said with what the person can do. The folder set aside is never listed by a look (only `originals/` and `renditions/` are), never in the index (made from records), and never a source (`made_by_keevoro` knows it by its note). The tests are `crates/keevoro-engine/src/put_right/tests.rs`, which builds the owner's backup as 0.42.0 left it (missing, short, one with other contents at the right size, and one a look wrongly said was short, with the records as that look wrote them) and proves one press ends with everything there and proved, the bad copies aside and the source untouched, and that a stop and a share dropping out are carried on from; and `what_check_they_all_arrived_finds_wrong_one_press_puts_right_and_the_screen_agrees` in `keevoro-api/src/jobs/tests.rs`.

The tests are in `crates/keevoro-engine/src/confirm/tests.rs` (the tester's case, one file gone, one cut short, the folder swapped for an empty one, unplugged at the start and part-way, a listing that fails part-way, another program finishing a file during the look, previews, nothing deleted, a check followed by a backup, and the same against a real S3 server where one is set up), `a_backup_deleted_from_its_folder_is_said_to_be_gone_before_anything_is_sent_and_is_sent_again` and its neighbours in `keevoro-api/src/jobs/tests.rs`, the command line's and the agent server's own versions, the app's wiring test and the browser test.

Video stills come from `keevoro-frame`, the one crate allowed `unsafe`, because it calls the operating system's decoder directly. Its Windows and macOS halves cannot be built on Linux, but they can be type-checked from anywhere:

```sh
rustup target add x86_64-pc-windows-msvc aarch64-apple-darwin
cargo check -p keevoro-frame --target x86_64-pc-windows-msvc --tests
cargo check -p keevoro-frame --target aarch64-apple-darwin --tests
```

Its real test (`tests/native.rs`) decodes a tiny sample video and only runs on Windows and macOS, so CI is where it proves itself.

### Finding where the photos are

Knowing which folder to point Keevoro at is the hard part on a big disk, so there is a survey that answers it first: `crates/keevoro-scan/src/survey.rs`. It reads folder listings only, the names and sizes a file manager shows, and never opens a file. That is why it gets through hundreds of thousands of files in seconds where a search takes much longer.

It is in two halves, kept apart on purpose:

- `survey` walks the disk on several threads and counts what each folder holds directly.
- `suggest` turns those counts into folders to offer. It is pure arithmetic and never touches the disk, so its rules are tested with made-up counts.

The rules in `suggest` aim for the folder a person would have picked themselves. A folder that is mostly photos and videos, everything beneath it counted, is offered whole (`Pictures`, not each of its two hundred subfolders). A folder with photos loose in it is offered too, so they are not lost. Anything else is only a container and its subfolders are considered one by one. A whole drive is offered only when nine files in ten on it are photos, which is a memory card and not a system disk. No suggestion is ever inside another.

A survey guesses from file endings (the list of kinds below), so it is a hint and nothing more. The person ticks folders and each becomes an ordinary source, searched properly. Try it from the command line with `keevoro survey D:\`.

### Looking inside a folder before choosing it

Each suggestion has **Look inside**, which opens a grid of its photos and a still of each video, folder by folder, before anything is added. It is read-only from end to end:

- **The outline is remembered, not walked again.** When a survey ends, its whole map (see [Where the space goes](#where-the-space-goes)) is written to `surveys/` in Keevoro's cache folder (`keevoro_engine::surveys`, lines of JSON named by a fingerprint of the place, at most eight places and 200 MB between them, the oldest forgotten first, though never the newest). `places.folders` answers from the newest one covering the place, with every folder in it that holds photos or videos itself (`Map::media_folders`), and never says anything outside the place asked about, so an agent allowed one folder learns nothing of the rest of a drive. Reset clears the cache, and the surveys with it.
- **One folder's files come from one listing.** `places.files` reads the folder's listing once (`keevoro_engine::look::list_folder`), keeps the last four in memory so paging is quick, and gives a page at a time by name. It lists only the kinds of file Keevoro looks for, and only photos or only videos when the backup in hand wants one kind. A folder Keevoro made (a backup, an old library) is refused with the same words a search uses, judged by itself alone as a search judges the folder it is pointed at.
- **A picture of any file.** `photos.picture` takes `file` as well as `photo`. `keevoro_engine::look::picture_of_file` never opens a file only in online storage, reads nothing else beyond the file itself, and writes only into the cache: the picture, named by the very fingerprint a search would give the file (`keevoro_scan::fingerprint`, the quick one the app's searches use), and an index, `look.sqlite`, that remembers which picture belongs to which file by its path, size and modified time, so a second look reads the picture back without reading the file, and a file that could not be shown is not tried again for a day. When the folder is later looked through properly, `preview_at` finds those pictures already made. They sit in the same cache as every other preview, under its 1 GB limit (below). Each drive has its own turns, taken before the three shared ones: one at a time across a network, two on a disk (`DriveTurns` in `keevoro-api/src/picture.rs`).
- **Any folder, in any order.** The look inside opens from a survey's suggestion, from a source's card and from "Look inside one first" on the first step, which picks a folder. When no remembered survey covers it, the app surveys it first, with progress and Stop (`folders_inside_if_surveyed` tells the app, which then runs `places.survey`). `places.files` takes `sort` (`name`, `newest`, `oldest`) and `only` (`all`, `photos`, `videos`, `others`), applied by the pure `arranged` in `inside.rs`; the dates are the files' own (when last changed), so the screen says "by file date" and never "taken". Each folder stays a section in path order whatever the sort, so a person's folders stay their organisation: a departure from the plan, which put the folder with the newest file first and would need every folder listed to know it.
- **Video lengths.** For the videos in the page asked for, and only those, `FileEntry::length` reads the movie header (`keevoro_scan::video::movie_header`, the same hop from box to box the search uses for the recording date): a few small reads, no decoding, and never for a file only in online storage. AVI and others whose container does not say have no length.
- **Pictures follow the check for duplicates.** A picture made while looking is named by the file's quick fingerprint. When the background check reads the file in full, `deep_look` (given the cache) renames its pictures and the index entry to the whole fingerprint (`look::now_known_as`), so the Discover grid finds them and nothing is made twice. Files that shared a quick fingerprint might have shared one picture, so theirs are left to be made afresh.
- **One limit for the whole cache.** `look::trim_cache` keeps everything in the cache (pictures, `look.sqlite` and the remembered surveys) within 1 GB, removing only pictures, those used longest ago first: reading a picture marks it used (`read_and_use`). It runs quietly at start-up and after every 500 pictures of any kind, one trim at a time. A picture removed while on screen is simply made again when next asked for, and in the window a picture whose address was let go is fetched again rather than shown broken.
- **The screens fetch only what is near.** `ui/src/tiles.tsx` (`VirtualTiles`) places every section and row from the counts alone, so the scroll bar is right at once, and draws only the rows within a screen above and below; each section's files are fetched a page at a time as they come near. Every small picture goes through `ui/src/pictureQueue.ts` (`PictureQueue`): four at a time, a request not started yet dropped when its tile leaves the screen, and the last 600 addresses kept, the oldest revoked (the old preview map never let go of one). The collection screen uses the same grid.

### Where the space goes

The owner pointed Keevoro at a large Pictures folder that also held zip files, texture packs, screen recordings and an old Keevoro library, and asked for a view like WinDirStat. So the map shows everything on the drive, photos or not, because that is what makes it useful for finding things; what is not a photo or video is muted, never hidden.

**How it is recorded.** The survey already reads every folder's listing, so it writes down what it saw in a map (`keevoro-scan/src/map.rs`), and the suggestions are worked out from that same map (`Map::tallies`, exactly the counts `suggest` always had, which its tests pin). For each folder: its name and its parent's index (never a whole path), what it holds directly by kind (photos, videos, everything else) in files and bytes, how much of that is only in online storage, its endings, and why Keevoro never looks through it, if it does not. Beside the folders, the biggest files by name and a table of endings. Nothing is opened: sizes and online-only attributes come from the listing, and a file only in OneDrive is never touched, its bytes shown as such.

**Suggestions first, everything else after.** A person is waiting on the suggestions, so the walk does them first and exactly as before. On a Mac or Linux a file's size is a question of its own, so at first only the photos and videos are sized (what the suggestions need); everything else in a folder is counted and sized in a second look once every suggestion is final. On Windows sizes come with the listing, so everything is sized at once. Folders Keevoro never looks through (system, app, hidden and developer folders, its own, a backup or old library, a folder left out) are listed last, only to size them. `SurveyProgress::sizing` says when that phase starts: the app then says "Now measuring the rest" with **Show the folders now**, which stops the survey losing no suggestion; the map then says what was not measured. On a made-up tree of 200,000 files (`how_long_a_survey_of_200_000_files_takes`, run by hand) the suggestions are final in the time the whole survey used to take.

**The map grows while it walks.** The builder keeps a running sum for each folder in the place surveyed, everything inside it counted in (`Builder::top`, a walk up the parents for each listing, never a pass over the map). Twice a second (`TOP_EVERY`) the survey's progress carries the biggest 48 of them, with the files directly in the place and the rest as smaller folders together (`SurveyEvent.top`, the same names as a box of `places.map`). In between it carries none, so other programs reading a job's last word are not burdened; the command line says only its counts. `ui/src/liveMap.tsx` draws them as the map is drawn, on the survey screen and wherever a place is surveyed first, each picture easing from the last over 400 ms unless reduced motion is asked for, and marked `data-easing` while it does.

**How it is bounded.** `map::Limits` holds every bound, so tests use tiny ones (`totals_stay_exact_when_every_bound_is_passed`). Past each bound only the identity of small things is lost, never a byte:

| What | Kept | Past the bound |
| --- | --- | --- |
| Folders | 100,000, one node each | The next folders are counted into the folder above, which says "and N more folders" |
| Files by name | At least 1 MiB, the biggest 64 per folder and 50,000 in all | The smallest is let go; its size stays in its folder's sums |
| Endings | 2,000 different ones, and 500,000 (folder, ending) pairs | Rarer endings are "other endings"; past the pairs, folders keep no endings of their own, and the totals for the whole place still have them |

A map of a million files in a hundred thousand folders holds about 25 MB (`a_map_of_a_million_files_stays_within_its_bounds` counts it). The walk holds it while it runs; once it is saved it is freed, and read back only when someone looks.

The folder bound was 500,000 at first. Measured with `how_much_a_map_at_the_folder_bound_holds` (run by hand on Linux, as it reads what the process holds), a map at that bound took 111 MB, allocator and all: about 220 bytes a folder, not the 80 the plan guessed (a node is 120 bytes, and its name and endings are allocations of their own). Being a good guest on someone's computer matters more than mapping half a million folders one by one, so the bounds are lower: at 100,000 folders, each with five endings and a file kept by name, a map takes 38 MB. Totals stay exact past every bound, and the bound bites late: a person's own folders are listed first, and the folders Keevoro never looks through (where most of a system disk's folders are) last, so on a whole disk it is the depths of system and app folders that are counted into the folder above.

**How it is remembered.** `keevoro_engine::surveys` writes the whole map into Keevoro's cache, as compact lines of JSON (format version 2). A survey remembered in the older, media-only form is simply surveyed again, and a file that does not hold together (an index pointing outside it) is ignored, so nothing read back can point anywhere it should not. The last map read is kept in memory, so going in and out of folders does not read it again.

**How it stays honest.** A folder's modified time only changes for what is directly in it, so there is no cheap proof that a deep tree is unchanged; instead a map says how old it is ("Mapped 3 days ago", with **Map again**), and `places.map` says when it is out of date (`refresh`): over an hour old, or a source in it looked through since. Every search (`sources.look`, `sources.look_again`) marks each remembered survey covering, or inside, what it looked through, with a small `.searched` file beside the survey's, gone when it is surveyed again (`surveys::mark_out_of_date`). Whether to map again is the pure `surveys::freshness`: on a disk of this computer the screen surveys again by itself as the map opens, showing the old map meanwhile; across a network (`reach::is_across_a_network`) it asks first, "This was mapped 3 days ago. Map it again? It may take a while over the network." A survey that was stopped is said as **Partly mapped**. `places.forget_maps` (`keevoro forget-maps`, and **Remembered maps** in Settings, Advanced) forgets every survey and the one held in memory, since a map lists folder names across a whole drive; it is for the person only, never an agent. Reset does the same as it clears the cache (`a_reset_removes_what_keevoro_made_and_nothing_else`).

**How it is asked.** `places.map` (`keevoro-api/src/space.rs`, `keevoro map`, the agent tool `where_the_space_goes`, and the app's `space_map`) takes a place, a folder inside it, a depth and the smallest box worth showing. The level of detail is pure Rust (`map::view`): a folder's subfolders and biggest files to the depth asked, the rest of its files of each kind as one box, subfolders too small to see merged, and never more than 8,000 boxes. What Keevoro would make of each box comes from the one rule, `keevoro_core::Choices::offered`, asked about each folder and ending (`Map::offered`), in its words: a folder Keevoro made, one the person left out, a kind switched off, or photos or videos the backup or a source does not want. Only the folder asked and what is inside it is ever said, and an agent must be allowed both the place and the folder, so a remembered survey of a whole drive tells an agent allowed one folder nothing else (`an_agent_allowed_one_folder_reads_nothing_else_of_a_remembered_drive`).

**What is a source and what is backed up.** Worked out each time `places.map` answers, from the backup in hand, and never kept in the survey, so it is always as it is now. A folder that is a source has `source`, one inside a source `inSource` (`Choices::sources`, compared as full paths, ignoring case on Windows). `backedUp: { files, of }` is how many of the files the backup keeps from a folder, everything inside it counted in, are safely at every place it goes: `keevoro_engine::safe_by_folder` counts them by folder with the very rule the Discover view and what is waiting at each destination use (`Reach::safe` in `discover.rs`, shared by all three, so there is one rule, and it goes by what the last look at each destination found; see [Is it really there?](#is-it-really-there-looking-before-counting)), and `space.rs` rolls them up the map; a file in a folder the map does not hold on its own counts in the nearest one it does. The map draws a source with a firm outline in the colour of safety and a folder wholly backed up with a tick in its corner where there is room; the list, the tooltip and the key say both in words.

**What a backup would take.** The summary line's figure ("This backup would take 26.3 GB of it") is `would_back_up` of the folder shown, from `Map::offered`: each folder's photos and videos by ending, judged by the one rule (`Choices::offered`), so a folder left out, a backup for photos only or a kind switched off take nothing, and a folder Keevoro made (a backup, an old library) or never looks through takes nothing however deep. A folder's endings are kept for every file, so its offer is held to what is left once the files no search takes are taken away: a Mac's `._` companion files, and anything counted in from a folder Keevoro passes by past the folder bound (`a_backup_is_never_said_to_take_what_no_search_would`; `the_map_says_what_the_backup_in_hand_would_leave_out_and_why` checks all of these at once).

**Show in File Explorer.** The chosen folder can be shown in the computer's file manager ("Show in Finder" on a Mac, "Show in Files" on Linux). The window's `open_place` asks `Keevoro::folder_to_show`, which allows only a folder on a remembered map, or one the backup knows (its own folder, a source or a folder inside one, a folder it is sent to), each compared in its full form, so `..` cannot climb out. It is for the window only (`WINDOW_ONLY` in `src-tauri/src/parity.rs`), never offered to an agent.

**How it is shown.** `ui/src/map.tsx` is the screen: the trail back up, the map, the list of what is in the folder shown, biggest first, with a share bar in the kinds' colours and patterns, and what can be done with the box or row chosen (look inside, look through it, leave it out or put it back) held at the foot of the window. Asking a place Keevoro has not surveyed surveys it first (`ui/src/surveyFirst.tsx`, shared with the look inside). What each box is called and says comes from `ui/src/mapWords.ts`, so the list, the map and its tooltip never differ. Beside **By folder**, **By kind of file** (`ui/src/mapKinds.tsx`) lists photos, videos and everything else in the folder shown, each opening to its endings, in the command line's words (`keevoro map --kinds`). Picking a kind or an ending fades every box on the map that holds none of it: each box of `places.map` carries `endings`, the places in the answer's `kinds` of the endings it holds, worked out by `map::view` (each folder beneath is given to the box it is shown in, its own, its parent's smaller folders, or the folder where the view stops). A box of a folder's own files of one kind is given all that folder's endings of that kind, so it can stay lit for an ending whose one file is shown as a box of its own.

**How the map is drawn.** The layout is `ui/src/treemap.ts`: the squarified layout of Bruls, Huizing and van Wijk (the biggest first, laid in rows along the shorter side, each row taking the next box only while that makes its worst box squarer). A folder at least 48 by 32 pixels is opened up, with an 18 pixel strip for its name and its contents inside; a box under 12 square pixels is not drawn on its own, and its room stays its folder's. It is pure, with nothing of the page in it, so `npm run ui:unit` tests it with Node alone (`ui/src/treemap.test.ts`: areas in proportion within half of one per cent, no overlaps, every box inside its folder, squarer than strips, nothing for nothing, the same layout every time, and thousands of boxes quickly), and it runs again on every resize without asking the API anything. `ui/src/mapCanvas.tsx` draws it on two stacked canvases at the screen's own resolution: the boxes underneath, drawn again only when the folder, the window's size or the theme changes, and on top only the outlines of the box pointed at, the row pointed at in the list and the box chosen, so moving the pointer never redraws thousands of boxes. A point is found by going down from the top through the boxes that hold it. Colours are read from the design tokens as it draws, so light, dark and a change of either look right. Since our first outside tester found a photo-heavy drive "a wall of orange", the boxes use soft tints of their own (`map-photo`, `map-video`, `map-carried`, `map-other`, each with an `-edge` at least 3:1 against the page and against its fill; labels are `ink` on every fill, at least 5.4:1), and the strong colours (`sun`, `pine`, `peach`) only fill the box chosen, on the canvas on top, with their paired `on-sun` and `on-primary` words. Each kind has a pattern (photos plain, videos striped, what Keevoro never looks through dotted, what is left out cross-hatched, what is only online dashed), with a key beneath in words, so colour is never the only sign. Going into a folder, its box grows to fill the map over a fifth of a second; coming out, the folder shrinks back into its box; with reduced motion asked for, the new map simply appears. While it eases the map is marked `data-easing`, which the browser test waits for rather than a set time. The canvas is an image to a screen reader, with a summary of what takes the room; the list carries everything else.

Above the map, `ui/src/summaryRing.tsx` draws a ring of the folder shown by kind (an inline SVG of `circle`s with `stroke-dasharray`, its patterns in `defs`, no new dependency), from the answer's own `photoBytes`, `videoBytes`, `carriedBytes` and `otherBytes`; the arcs are worked out by the pure `ringParts` (`ui/src/ringParts.ts`: parts of nothing left out, a part over nothing given at least 1.5% of the circle to be seen while its figures stay exact, the arcs adding to 360). The ring is `aria-hidden`; its figures are a real list whose items pick a kind, which is the same `picked` the "By kind of file" tab uses. Beside it, "Map" and "List" choose the view (`ui/src/spaceView.ts`): the list alone draws no canvas and widens the share bars. The choice is how a window draws, like the theme, so it is kept in `localStorage` (`keevoro-space-view`), never in the register; unset or unreadable, it is the map.

Small folders are gathered on the screen, never by the API: `gathered` in `treemap.ts` puts the folders (and the API's own "smaller folders" box, but never a file, a source of the backup, or a single folder) that are each under a share of the folder they are in into one box, made by `together` in `mapWords.ts`, which adds up every figure so what it holds, whether it is all backed up and which kinds it holds work on it unchanged. The share is `gatherShare`: what a readable box (`Spacing.readable`, 96 by 40 pixels) would take of the folder's box, kept between 2% and 10%, so a big window gathers less; the list follows the map's share for the folder shown (2% in the list alone). It is one pass before the sort the layout already does, so the layout stays as quick (`treemap.test.ts` lays out eight thousand boxes, gathering on, within the same bound). A click on the gathered box opens it as if it were a folder, with "Smaller folders" as the last step of the trail, and Back or the trail closes it; in the list it is a disclosure that opens in place, its folders indented. The demo's family drive (`FAMILY_DRIVE` in `ui/src/demoMap.ts`) is nearly all photos, as the tester's was, with thirty small albums to gather. Below 760 pixels the list goes under the map, and below 480 the map is a strip of the biggest boxes until **Show the map** is pressed.

New screens and the pieces they share go in files of their own under `ui/src/` (`inside.tsx`, `tiles.tsx`, `pictures.tsx` for `Picture` and `Viewer`, `pictureQueue.ts`, `tidy.tsx`, `leaveOut.tsx`, `map.tsx`, `mapKinds.tsx`, `liveMap.tsx`, `surveyFirst.tsx`, `licences.tsx`, `wants.tsx`, `otherFiles.tsx`, `whatIsThere.tsx` with `thereWords.ts`, `manageBackups.tsx`, `checking.tsx`, `noReload.ts`, `arrange.tsx`, `summaryRing.tsx` with `ringParts.ts`, `spaceView.ts`, `synced.tsx`, `storageForm.tsx`, `bucketSource.tsx`, `differentDrive.tsx`, `byItself.tsx`, `schedule.tsx`, `putRight.tsx`, `tray.tsx`, and Settings in `settings/`), imported by `App.tsx`, rather than growing `App.tsx` further. Do the same for the next screen.

### Settings

Settings is `ui/src/settings/`. While it is open it has the whole window: `shell.tsx` puts its own short list of sections where the side bar was, so there is never a second side bar beside the first, with a search across every row above the list and the section chosen beside it. Below 640 pixels the list is a page and each section the next, as on a phone. Where Settings was is kept by `App.tsx` for as long as Keevoro is open, so it opens there again.

- **Where everything is** is `places.ts`, pure and tested by `npm run ui:unit`: the sections in order (everyday first, then Advanced and Help set apart), the pages that open from a row (`DETAILS`), and every row by its name, with the other words a person might search for it by (`ROWS`). The search, the links from elsewhere in the app and the icon by the clock all find a row there, so they cannot disagree.
- **Each section is a file** (`thisBackup.tsx`, `backingUp.tsx`, `appearance.tsx`, `updates.tsx`, `advanced.tsx`, `help.tsx`), and so is each page inside one (`fileKinds.tsx`, `agents.tsx`, `log.tsx`; the licences are the list in `ui/src/licences.tsx`). They are built from `parts.tsx`: `Group` (a rounded panel of rows, with a small heading above and a footnote below), `Row` (the name on the left, at most one quieter sentence beneath, the control on the right), `RowSwitch` and `RowButton` (named and described by their row, for a screen reader), `OpenRow` (a row that opens a page of its own, with a chevron) and `Said` (what a change means, under its panel, its two lines kept when empty so nothing moves when it is said).
- **One family of switches.** In Settings every setting that is simply on or off is the full-size switch on the right of its row. Outside Settings, a switch that sits beside its words among other things (a source's own choices, the first-close explanation, the kinds table) is the small `Toggle` (`ui/src/toggle.tsx`). Choosing several things out of a list keeps its ticks, and how files are arranged keeps its two radio choices, since each needs its sentence to be understood.
- **Going to a row.** A link elsewhere in the app opens Settings at a row with `openSettings(placeOfRow('previews'))` in `App.tsx`; the icon by the clock sends a page name, `settings`, `settings/byItself` or `settings/byItself/keepRunning` (`parsePlace`). The row is brought into view, its control is given the focus, and it is marked for a moment (`data-marked`). Add `?page=settings/advanced/kinds` to the address in the browser to do the same.

**Adding a setting.** Decide which section a person would look in first; if most people never need it, it is Advanced. Add its row to `ROWS` in `places.ts`, with a name that makes sense on its own (a thing, or a plain statement such as "Start Keevoro when this computer starts") and the words someone might search for it by. Then add a `Row` to that section's file with one short sentence and its control: a `RowSwitch` for on or off, a `RowButton` for something done, an `OpenRow` and a page of its own for anything long. Anything that cannot be undone goes in a `Group` of its own with `danger`, asks in the page first, and says what it does and does not touch. Find it by its name in the browser test (`scripts/ui-test.mjs`). Wherever a sentence tells a person where it is (in the app, the command line, an agent's refusal, these docs), name it the way the screen does: "Settings, Advanced, AI agents".

### Open source licences

About, and Settings, Help, have **Open source licences** (`ui/src/licences.tsx`): every third-party Rust crate and npm package shipped in the app, with its licence. The list is `ui/src/licences.json`, made by `cargo xtask licences` (`crates/xtask/src/licences.rs`): the crates come from `cargo metadata`, following only the normal dependencies of `keevoro-app` and `keevoro-cli` (nothing only for building or testing), and the npm packages from `package-lock.json`, leaving out those marked `dev`. Crates for every platform are listed, since the same list ships everywhere. When a dependency changes, run `cargo xtask licences` and commit the file: `the_list_of_licences_kept_is_up_to_date` (in `cargo test`) and `cargo xtask licences --check` (in CI's lint job) fail until you do. ### The kinds of file Keevoro looks for

Which endings count as photos and videos is a list the person can change, in Settings, Advanced, Kinds of file, or with `keevoro kinds`. It is one list for the whole of Keevoro, not one per backup, and it is separate from leaving out a kind of file on one source (`sources.include_type`), which works on what was found.

How it flows from a click to a search:

1. **Kept as changes.** `keevoro_core::kinds` holds the built-in list (`BUILT_IN`) and the rules. The settings file keeps only what the person changed (`file_kinds` in `settings.json`): endings they added, and built-in ones they switched off or made the other kind. So the list always starts as the built-in one, a built-in kind added in a later version simply appears, and a settings file nobody changed is written exactly as before. It is changed under the settings lock like everything else there (`Backups::change`), so two programs never undo each other.
2. **Read once per job.** When a search (`sources.look`, `sources.look_again`) or a survey starts, `Keevoro::kinds_to_look_for` reads the settings once and makes a `Kinds`, a small lookup by ending. It goes into `ScanOptions::kinds` or `survey`'s `kinds` argument. Nothing consults the disk per file, and the pure functions take the list as an argument, so they are tested with lists made up in the test. A change made while a search runs counts from the next one.
3. **Asked about each file.** The survey counts a file when `Kinds::looked_for` knows its ending. The search passes over, unopened, a file whose ending is switched off, and plainly-not-media endings as before. For a built-in kind Keevoro recognises from inside (a JPEG, an MP4) what is inside still decides: a `.jpg` that is really text is not a photo. For a kind known only by its name (most camera raw and camcorder kinds, and every kind a person adds) `Kinds::by_name` gives the answer when the inside does not say it is a photo or a video, so such a file is found even though nothing can open it. A file whose ending is not on the list at all is still opened and judged by what is inside, so a photo called `IMG_0001.dat` is not missed.
4. **Nothing found is taken away.** `keep_found_before` in `keevoro-engine/src/lib.rs` keeps, when a source is looked through again, any file found there before whose kind is no longer looked for, as long as it is still there at the same size. Switching a kind off changes what is looked for from now on; it never drops a file from the list, from the next backup's index, or from anywhere it was backed up.

A kind Keevoro cannot open goes through everything else like any other file: it is fingerprinted, told apart from its copies, placed in its collection, and copied and proved exact. With no pixel size it is never set aside as tiny. Making its preview fails quietly: the catalog remembers `NoPreview` so it is not tried again, nothing is logged, the index lists it without previews, and the screens show their "No preview" square. `a_kind_added_that_keevoro_cannot_open_is_found_and_backed_up_exactly_with_no_preview_and_no_fuss` in `keevoro-api/src/jobs/tests.rs` walks that whole path.

The guard on what may be added is small: an ending is letters and numbers only (no spaces, dots or path characters, at most ten), compared without case or the leading dot, and never twice. An ending Keevoro passes over as programs, documents, music or archives (`never_media_extension`) can never be a photo or a video, which would make no sense to look inside; it can be added as an other file instead, and the refusal says so ("To back them up as they are, add .pdf as an other file."), with a button in the app that does just that. An AI agent may read the list (`list_file_kinds`) but not change it, like Keevoro's other settings.

### Other kinds of file, carried along

Keevoro is a photo and video tool, but a person can have it take other files with it: music, documents, project files. The backup itself never minded what a file is; what is particular to photos and videos is the grouping, the previews and the words. So a third kind, `MediaKind::Other`, goes through everything the other two do, and only those three things are different.

How one flows from a click to a backup:

1. **A person adds it.** In Settings, Advanced, Kinds of file, "Add a kind of file…", or `keevoro kinds add flac --other`, `file_kinds.add` with `kind: other`. Any ending can be, even one passed over as never a photo (`FileKinds::add` refuses those only as a photo or video). Nothing is an other file until someone adds one, so out of the box Keevoro finds exactly what it always did (`nothing_is_an_other_file_until_a_person_adds_one`). Only three system files are never taken whatever is on the list, by name, in `SkipRules::skip_file`: Windows' `pagefile.sys`, `hiberfil.sys` and `swapfile.sys`, and the Mac's `sleepimage`, each the size of the computer's memory and locked while it runs; nothing is refused by ending.
2. **A search finds it by its ending alone.** `examine_other` in `keevoro-scan` reads the file only to fingerprint it (quickly sampled when large, like any file, and read in full before anything counts), never sniffs, sizes or dates it from inside, and never sets it aside as junk. Its album is the folder it came from, starting with the source folder's own name, exactly as the person arranged it; its date is when it last changed. A file only in online storage is never opened, as for photos.
3. **Duplicates, places, sending and proving are the same code.** Copies are told apart by fingerprint, the copy kept is chosen by the same rule, and `agree_places` gives it a place under `originals/Other files/<its folders>/<its name>` (`keevoro_core::layout::library_folder`), a clash numbered `return (2).pdf` as for photos. It is sent and proved exactly like any original, and listed in the index as type `other` in an album named after its folder; the old `gallery.json` shows photos only. No preview is attempted: the background leaves it out of what is still to make, and `preview`, `picture_of_file` and the closer look refuse before opening it (`NO_PICTURE_OF_OTHER_FILES`). The guide note says where other files are, only when the backup holds some (`layout::guide(true)`).
4. **Listed by folder, not by date.** `group_into_collections` makes one collection per folder of other files (`Collection::by_folder`), after every collection of photos and videos, in folder order, its key starting `Other files / `. So keeping or leaving out a folder is `collections.keep`, a file `photos.keep`, and the plan, the estimate, the room check, what is waiting at each destination and the history all count them with no change. The app shows them in their own section, "Other files", under the collections (`ui/src/otherFiles.tsx`): a row per folder with its count, size and Keep switch, opening to a plain list (name, kind, size, when it last changed) with a tick each, and a file's details with Show in File Explorer. Wherever a picture would be (a duplicate, a look inside), `FileTile` shows its name and kind instead.
5. **What a backup or a source is for.** `keevoro_core::Wants` is three ticks, photos, videos and others, at least one, stored as the list (`["photos","videos"]`) and everything unless chosen. "Other files" is only offered, and only spoken of, once a kind of them is on the list (`Wants::words(others_listed)`, `offersOthers` in `backup.wants`), so a person who never adds one reads "photos and videos", "photos only" as ever. The rule that applies it is still `Choices::offered`, which says what left a file out with the choice itself (`LeftOutBy::Backup(wants)`).
6. **The survey, the look inside and the map.** A kind on the list as other is counted as wanted (`Tally::carried`), so a folder of only those can be suggested ("4,120 other files"). The map has a fourth kind, `map::Kind::Carried` (`carried` in its answers, beside `other` for everything else), drawn in peach with level lines like writing and named "Other files to carry along" in the key, the list and the kinds tab, only when there are some. A remembered map is written with them last, so one remembered before has none and reads as it was.
7. **Counted and said one way.** `keevoro_core::words::files` says "238 photos, 11 videos and 40 other files" for the screens' figures and `words::photos_and_videos` the command line's ("30 photos and 2 videos", both always named); `ui/src/format.ts` has `files` too, and both are tested against one table, `ui/src/countWords.json`. Every new field (`others`, `carried`, `byFolder`, `isOther`, `offersOthers`) is left out of an answer when there is none, so the JSON is as it was. `a_person_who_adds_no_kind_of_other_file_sees_nothing_new_anywhere` in `keevoro-api/src/jobs/tests.rs` holds all of this, and `other_files_carried_along_are_surveyed_found_kept_by_folder_backed_up_exactly_and_an_agent_keeps_within_its_folders` walks the whole path, an agent included.

Music done properly (artists, albums, cover art) is a later step, and only if carrying music along this way proves to be used.

### Keep my folders as they are

Our first outside tester's source was `Pictures / Scans / Family Scans`; by date, the scans went under `By date / 2021 / 2021-01`, the day they were scanned. So a backup, or one source, can keep its folders exactly as they are instead (`keevoro_core::arrange`): a photo or video's folders are the source's own folder name (`top_folder`: a whole drive is named by its label without `(E:)`, else `Drive E` or `share on server`) then every folder below it (`kept_folders`), with nothing trimmed as noise and nothing put by date. Other files already kept theirs, under `Other files`; photos kept by folder sit beside named albums, `originals/Family Scans/Smith/a.jpg`.

It is applied in one place, in memory: `Catalog::load_reports` gives such a file those folders as its album, with `FolderHints::kept` set, so collections, places, the index and the guide all follow with no other change. Nothing is written back; `Catalog::load_reports_as_found` gives the albums as found, for what a search writes back. The choice is the catalog setting `arrange` (`"byDate"` or `"folders"`), a source's is `arrange:<its place>`; missing means by date. Catalog step 12 writes `arrange = "byDate"` into any catalog that already holds anything, so a backup made before the choice existed is by date and is not asked; a new one is asked the first time it is set up (`backup.arrange` answers `asked`). A backup run before anyone was asked (from the command line, say) goes by date and says so once at the end.

A file's place is agreed once, so changing the choice changes only what is placed from then on. `follow_a_changed_arrangement` (in `check_and_place`) compares the arrangement now (`arrangement_said`) with the one places were last agreed under (`arranged_as`); only when they differ does it walk the chosen files, and of those whose place no longer matches, `Catalog::forget_unsent_places` frees only the ones no destination has any record of (found there or not), with no upload in parts and no copy here. A file sent anywhere keeps its place, so it is never moved, never sent twice, and the look at each destination still finds it where it was sent (`changing_how_a_backup_is_arranged_moves_nothing_and_sends_nothing_twice` in `keevoro-engine/src/arranging_tests.rs`). A destination added later gets it at that same place. When the choice changes after anything was sent, `arrange_changed_at` is kept, and the guide says from when (`layout::GuideFacts`). When the same photo is in a source that keeps its folders and one that goes by date, the copy kept is the kept-folders one (`how_well_described` in `summary.rs`, shared by the list of duplicates and what is sent, so they cannot disagree), unless that photo already has a place.

In the app (`ui/src/arrange.tsx`), the question is asked once, the first time a backup that has found something and has not been asked (`asked` false) moves on from finding, by its button or the side bar: it is part of Find, so the side bar stays there and Back goes back. Next writes the choice. Settings, This backup, has the same two choices for the whole backup, as rows of one panel, and File types beside a source a native select with the suggestion and a button to take it. `?demo=scans` opens the demo on a new backup holding a folder of family scans, as the tester had. On "Choose what to keep", each folder kept as it is is one collection (`Collection::kept_folders`, its key starting `Kept as they are / `), after the dated ones, in folder order, with no date range. Keevoro suggests which to choose from what was found (`arrange::suggest`, pure, one pass over a source's photos and videos, no disk and no query per file, worked out only when `backup.arrange` or `sources.arrange` is asked). The first rule that holds wins, with its thresholds as named constants: it looks like scans (a folder called scan, scans, scanned or scanner, or half the names start with "scan"); 80% would go into Undated; the commonest day holds 80% of those dated to the day; 70% sit in at least three folders with real names and the source's own name is not noise; or (for by date) half sit in camera folders and the dates spread over at least seven days. Fewer than 20 files suggest nothing. For the whole backup, the suggestion covering the most bytes is given, saying why from the biggest source it came from, with `sourcesDiffer` when they disagree. A source's answer carries its suggestion only when it differs from what the source does now. The words are `Suggestion::why_for_the_source` and `why_for_the_backup`, so every front end says the same.

`backup.arrange` (`keevoro arrange`, the agent tool `backup_arrange`) reads and sets it, and `backups.start` takes `arrange`; `sources.arrange` (`keevoro sources arrange`, `source_arrange`) does the same for one source. Two sources whose top folders have the same name (compared without case) both keeping their folders share that folder, exactly as other files do: an exact copy is one file by fingerprint, and a different file with a name already taken is numbered. Each source's card says so, from `SourceView::shared_said` (`arrange::sharing_a_folder` and `shared_words`, pure, so the app, the command line and an agent say the same).

### What a backup is for, and folders left out

Which files are offered is decided by one pure function, `keevoro_core::Choices::offered` (in `wants.rs`), which composes every choice in one order, broadest first, and says which one left a file out (`LeftOutBy`): a folder Keevoro made, then a folder the person left out of the backup, then the kinds of file Keevoro looks for at all (above; a kind switched off is never found, so this is only ever said when looking inside a folder), then what it is for, photos, videos and other files (a source's own choice if it has one, otherwise its backup's; `backup.wants` and `sources.wants`), then each ending on a source (`sources.include_type`). `Catalog::choices` gathers them for one backup. The "File types" list, the look inside (each tile marked "Left out", and the closer look saying why) and `places.files` (`leftOut` on each file) all say it in words ("left out: this backup is for photos only"). The backup's choice is the catalog setting `wants`, a source's is `wants:<its place>`, the folders are `left_out_folders`, and all are applied in `Catalog::load_reports`, the one place everything reads what was found, so it counts at once with no new search, and every count, the plan of a backup, the estimate and the room check follow it. Nothing already backed up is touched. A survey for a backup that wants only some kinds counts only those (`Kinds::wanted_by`).

A folder is left out with `sources.leave_out` (`keevoro sources leave-out FOLDER [--put-back]`, the agent tool `leave_out_folder`, and in the app "Leave out" beside each survey suggestion, each folder in the look inside and the look inside itself, with "Put back" there, under each source and in what a search or survey passed by). It belongs to the backup, may be a folder in no source yet, and is kept as its real path. Asked to look through a place left out, Keevoro refuses and says to put it back first, and looking again passes a left-out source by, so what was found there is kept for when it is put back. `Keevoro::skip_rules_for` adds a backup's folders to the rules of its searches and surveys (`SkipRules::with_left_out`), which pass them by without listing them, and say so as `SkipReason::LeftOut` ("leftOutByYou", which can be put back). Folders are compared by `keevoro_core::places::within`: by their parts, so `Photos 2` is never inside `Photos`, ignoring case on Windows only, and always on real paths, never a path as typed against a real one. A folder that has gone can still be put back, by the very words Keevoro gave for it. An agent needs changes allowed and the folder allowed.

### What a search and a survey leave out

`keevoro_core::SkipRules` decides which folders are never looked in: system and app folders, recycle bins, hidden folders and developer folders, by name, and Keevoro's own folders, by what is in them. The search (`keevoro-scan/src/lib.rs`) and the survey (`survey.rs`) both use it, and every folder left out is in the report with its `SkipReason`.

Keevoro's own folders are never a source, because backing a backup up into another is never what a person means:

- **A backup**, wherever it was sent and whatever it is called: a folder holding the note `What is in this backup.txt` beside an `index` folder (`SkipReason::KeevoroBackup`). The whole folder is left out, originals included.
- **A library from before 0.30**, the gathering model that was removed: `.keevoro/catalog.sqlite` beside an `originals` folder (`SkipReason::OldLibrary`). It holds copies of photos, so it is described (how big, how much is copies and how much previews) and never removed; the person decides.
- **A backup's own folder** (`.keevoro/catalog.sqlite` alone), and Keevoro's data, config, cache and log folders (`SkipReason::KeevoroOwn`).
- **Every folder a backup on this computer goes to**, by its full path, even before its first backup has written anything there. `Keevoro::skip_rules` (`keevoro-api/src/jobs/own.rs`) gathers these from the settings as each search or survey starts.

The survey only looks closely at a folder when one of those telltale names is in its listing, so it stays quick. Each folder left out is said, in the log, at the end of a search (`ScanEvent::left_out`) and of a survey (`SurveyView::left_out`), in the app as one quiet line that opens, and at the command line. Files found there by an earlier search drop out of what is offered at the next look, and the line says how many; anything already backed up stays backed up. To back up a backup's photos somewhere else on purpose, a person chooses its `originals` folder itself as the source: only the folder chosen is judged, never its parents, so that works, and an AI agent is still held to the folders it is allowed. Keevoro's previews copied out of a backup by hand (loose `.webp` files) are not recognised; nothing marks them as Keevoro's.

The walk has no depth limit and never follows a link or junction, so a loop cannot happen and nothing is counted twice; a photo reached only through a shortcut or junction is found where it really is, if that place is looked through. A folder that cannot be opened is reported and the walk carries on. Long names, names in any language, and (from other computers) names ending in dots or spaces do not stop it; `how_deep` in `keevoro-scan/src/tests.rs` pins all of this for the search and the survey. On Windows a path longer than 260 characters works throughout, because the source is canonicalised and Rust's file functions use the long form; `a_photo_with_a_path_longer_than_260_characters_is_found_pictured_and_backed_up` proves it on CI. A file only in online storage (OneDrive's "files on demand": recall on open or on data access, or offline; on a Mac, iCloud's "dataless" files) is passed over without being opened, since opening one downloads it; one found before stays found. Only a file that could be a photo or a video is asked about, and only by its attributes as the folder listing gives them, through the small `OnlineCheck` trait in `keevoro-scan/src/online.rs`: `ByAttributes` reads Windows' attributes or the Mac's file flags (cfg-gated), the pure `windows_online_only` and `mac_dataless` decide and are tested everywhere, and tests hand the search and the survey a check of their own (`ScanOptions::online`, `survey`'s `online`), so Linux CI covers the rest. How many is never only in the log: the search's last word (`ScanEvent::online_only` and `online_only_said`), each survey suggestion (`HintView`) and the survey as a whole, and each source (kept in the catalog until it is looked through again or forgotten, so it is still said after the person goes elsewhere) all carry the count and one sentence from `keevoro_engine::summary::online_only`, which the app, the command line and an agent's summaries show as it is. See [Cloud drives as sources](#cloud-drives-as-sources) for how each file and its size are kept.

### Cloud drives as sources

Our first outside tester asked whether Keevoro could back up cloud drives, combine several, and move to a cheaper cloud. The owner chose two steps: the folders the services keep on the computer, done properly, then cloud storage (a bucket) as a source. Signing in to a service directly is for later.

**Synced folders, offered by name.** `keevoro_core::synced` decides, pure, which folders OneDrive, Dropbox, Google Drive and iCloud Drive keep on the computer, from `ComputerFacts`: the system, the home folder, a few variables of the environment, the text of Dropbox's `info.json`, the listing of `~/Library/CloudStorage`, the drives' labels, and which of the folders it suggests exist. Its tests give it the facts of a Windows computer, a Mac and Linux on any computer. `keevoro-api/src/synced.rs` gathers them (the functions `files_to_read`, `folders_to_list` and `places_to_check` say what to ask), reading nothing inside a cloud folder, and keeps the answer for `places::KEEP_FOR`, half a minute, as the network drives are. `places::plugged_in` adds each as a `Place` with `synced` (the service), after the drives; a drive that is a service's own (Google Drive's `G:`) is offered once, as the service. The app's `places` command already runs on a thread of its own, so the window never waits; on Linux gathering took about 0.1 ms in a debug build (`finding_the_synced_folders_is_quick_and_asking_again_is_quicker` prints it), and two asks within half a minute cost a lock. The cards are `ui/src/synced.tsx`, plain buttons like a drive's, never shaded as chosen.

Where each service is looked for, and how sure we are:

| Service | Windows | Mac | How sure |
| --- | --- | --- | --- |
| OneDrive | `OneDriveCommercial`, `OneDriveConsumer` and `OneDrive` in the environment (OneDrive sets them for each account), then `%USERPROFILE%\OneDrive`. A work folder is named by its own name, "OneDrive - Contoso" | Each `OneDrive-…` folder in `~/Library/CloudStorage` (`-Personal`, or the organisation; SharePoint's `SharedLibraries` left out), then `~/OneDrive` | High |
| Dropbox | `info.json` in `%LOCALAPPDATA%\Dropbox` or `%APPDATA%\Dropbox` (`personal` and `business`), then `%USERPROFILE%\Dropbox` | `~/Library/CloudStorage/Dropbox` (and `Dropbox-<team>`), `~/.dropbox/info.json`, `~/Dropbox` | High for `info.json`; medium for the CloudStorage name of a team |
| Google Drive | The drive labelled "Google Drive" (streamed), then `%USERPROFILE%\My Drive` (mirrored) | `My Drive` inside each `GoogleDrive-<account>` in CloudStorage, then the old `/Volumes/GoogleDrive` | Medium |
| iCloud | `%USERPROFILE%\iCloudDrive` and `%USERPROFILE%\Pictures\iCloud Photos` | `~/Library/Mobile Documents/com~apple~CloudDocs` | High on a Mac; medium on Windows |

Linux has only Dropbox's `info.json` and `~/Dropbox`. The plan read Windows' registry too (OneDrive's `Accounts` keys and the `SyncRootManager` every cloud-files provider registers in); that needs a new dependency or unsafe code outside `keevoro-frame`, and the environment already names every OneDrive account a person is signed in to, so it is left until a real computer shows a folder this misses.

**Files only online, remembered.** A search already passes over, unopened, a file only in online storage (see [What a search and a survey leave out](#what-a-search-and-a-survey-leave-out)). It now keeps its size too, from the listing it already has (`ScanReport::online_only_bytes`, beside `online_only`), and catalog step 13 keeps each such file in the `online_only` table (`source_id`, `path`, `bytes`), written by `save_scan` and gone with the source; the count setting `online_only:<root>` is still written for older versions. `Source::online_only_bytes` is their size together, `None` for a source last looked through before step 13, which says its count as it did (the 0.37.1 fixture checks it). `summary::online_only(n, bytes, place)` says, for example, "412 files, 18.4 GB, are in OneDrive only, not on this computer, so Keevoro did not open them. To include them, make them available offline in OneDrive first, then look again.", naming the service from the folder's own names (`synced::service_of`) or this computer's. `Catalog::online_only_files` gives each file and its size: the seam for fetching them, a few at a time, which waits on the owner, because freeing a fetched file again sets an attribute on a file in the person's cloud folder, an exception to "never write to a source". Until then, the sentence says what a person can do.

**A bucket as a source.** A bucket, or a folder in one (its prefix), on Cloudflare R2, Amazon S3, Google Cloud Storage or other S3-compatible storage, can be a source: `sources.add_bucket` (`keevoro sources add-bucket`, the agent tool `add_bucket_source`, "Add cloud storage as a source…" in the app, `ui/src/bucketSource.tsx`, whose questions are the destination form's own, `ui/src/storageForm.tsx`).

- **Where it is.** `keevoro_core::bucket::BucketPlace` (kind, place, bucket, prefix; nothing secret). Its root reads like a place, `s3://family-photos/Photos`, and each object's path is that root, `/`, and the rest of its key, so collections, places, kept folders, `wants:` and `arrange:` work by path as for a folder. A drive letter is one letter, so such a path is never a real folder, and `is_bucket_path` tells them apart wherever a file would otherwise be opened. Catalog step 14 adds `sources.kind` (`folder` for every source before) and `sources.place` (the place as JSON), which `save_scan` carries over each look; `Source::bucket` gives it back, and `SourceView::bucket` says it in words.
- **Only ever read.** The engine is given a source bucket only as `keevoro_storage::ReadOnly`, which holds the store privately and offers listing and reading: no code given one can put, replace or delete anything, and two `compile_fail` doctests prove a write does not compile. Keys are tested with `ObjectStore::check_reading`, one page of listing, never the probe a destination writes. The engine's tests (`crates/keevoro-engine/src/bucket/tests.rs`) run against `NoWrites`, a store that refuses and counts every write, and compare every byte and file time of the bucket before and after; where a test server is set up, `against_a_real_server_a_bucket_source_is_added_looked_through_and_backed_up_and_never_changed` does the same through `send::everywhere` and checks each object's tag is unchanged.
- **Keys.** As a destination's (see [The API](#the-api)): a `Key` that cannot be shown, `keys_to_use` (given, else saved, else the environment's, said), the keychain under `BucketPlace::secret_name` (`source:…`), taken out of any error, and forgotten with the source or when its backup is cleared away (`connect::keys_kept_for`). `a_key_given_is_never_given_back_shown_logged_or_written_down` and the command line's own key tests give marker keys to `sources.add_bucket` too.
- **Looking through** is `keevoro_engine::bucket::look_through`: one paged listing (`ReadOnly::list_page`, up to a thousand objects a page, stop and pause between pages), turned into a search's report by the pure `keevoro_scan::bucket::found_in_listing`. Kinds come from endings (`Kinds::looked_for`), as in a survey; the date from the name, else when the object was written (`DateSource::Modified`); folders from the key; a Keevoro backup inside the bucket is passed by (`made_by_keevoro`, by its note beside `index/`), unless its `originals` are chosen; hidden and system folders as on a disk. Each object's fingerprint is `bucket::quick_fingerprint` (its root, key, size, tag and time): unique to the object, so nothing looks alike by it, and the same each look, so `save_scan` keeps the whole fingerprint learnt when it was backed up and a second look reads nothing. Inside a Keevoro backup's `originals` the whole fingerprint Keevoro labelled each object with (`x-amz-meta-blake3`) is read with a small request each, 16 at a time, and used as its fingerprint, so copies are known without a download; it is checked against what is read when the object is backed up. Objects in Google's colder classes (`NEARLINE`, `COLDLINE`, `ARCHIVE`) are read at once, at a charge, so they are found and backed up like any other; `keevoro_core::bucket::costs_more_to_read` picks them out, and `look_through` counts them in the catalog setting `colder:<root>` ("count bytes"), said as `colderSaid` on the source ("2 files, 8.6 MB, are in Google’s Nearline, Coldline or Archive storage, which costs more to read out. Keevoro backs them up all the same."). Objects in archive storage (`GLACIER`, `DEEP_ARCHIVE`) are kept with the files only online, with their size, and said: "1 file, 8.6 MB, is in archive storage, which can't be read until it is restored. Keevoro can't do that yet; to include it, restore it in Amazon S3 first, then look again." The background check for duplicates never reads a bucket's files (`Catalog::unhashed` leaves them out), and neither does `check_and_place`.
- **Backing up** goes through `keevoro-publish` as any file does, with `Upload::fetch` set (`bucket::Buckets::fetch_for`, opened once per backup with the saved keys). When its turn comes the object is downloaded into `<home>/.keevoro/fetching` (`ObjectStore::download_to`, streamed and fingerprinted as it is written, into a new file, removed on any failure), only if there is room for it and `ROOM_TO_SPARE` (2 GB) besides; a dropped connection is tried again with the usual retries. `send_one` then refuses it if it is not what Keevoro labelled it, leaves it out if it is an exact copy of a file already given its place (in the catalog, or sent earlier in the pass: `PublishReport::copies_left_out`), and otherwise sends it from the copy here labelled with its fingerprint, so a folder proves its copy against it; the copy is removed however that went (`Fetched` removes it when dropped). However many files are being sent at once, never more than two fetched ones are on this computer at the same time (`FETCHED_AT_ONCE`, held in `publish`), and the staging folder is cleared when a backup starts. A file already safely at a destination is never read again. Previews are not made of a bucket's files, since that would mean downloading them (`NO_PICTURE_IN_CLOUD_STORAGE`); C2.4 would make them from the destination's copy.
- **Google Cloud Storage** is the kind `gcs`, through Google's S3-compatible (XML) API: `Preset::GoogleCloud` in `keevoro-storage-s3` is `https://storage.googleapis.com`, region `auto`, the bucket in the path, with HMAC keys (an access key starting `GOOG`). Its place is always `storage.googleapis.com` (`keevoro_core::bucket::GOOGLE_PLACE`), filled in by Keevoro, so `place` may be left out of `destinations.add` and `sources.add_bucket` for it. Write-once is asked for with `x-goog-if-generation-match: 0` (`GOOGLE_WRITE_ONCE`) on a plain upload and on starting and finishing one in parts, instead of `If-None-Match: *`. Every kind is sent the same plain requests, with no `x-amz-checksum-*`, trailer or `aws-chunked` encoding (`RequestChecksumCalculation::WhenRequired`, as for R2); `google_is_sent_plain_requests_and_asked_for_write_once_in_its_own_words` checks the requests byte for byte against a stand-in server. Nothing uses `DeleteObjects`, which Google's XML API lacks. A saved destination of a kind this version does not know (one a later Keevoro added) is refused by `Saved::open`, never taken for a folder.
- **Comparing what cloud storage costs** is Stratus, by Adam Sparshott, used live and never copied (the owner's decision: a copied price goes stale between releases). "Not sure where to buy cloud storage? Compare providers" on "Where should they go?" (`ui/src/compare.tsx`) opens a sheet holding `https://stratus.adam-sparshott.workers.dev/#embed` in a frame with `sandbox="allow-scripts allow-same-origin"` (its own origin, so its messages can be told apart; no popups, top navigation or forms) and `referrerpolicy="no-referrer"`. Nothing is loaded until it is opened. The pure part is `ui/src/stratus.ts` (tests in `stratus.test.ts`): `readMessage` believes only that exact origin and keeps only the fields Keevoro uses, checked, shown as text; on `{stratus:'ready'}` the sheet posts `setMessage` (`{stratus:'set', need, currency, kind:'object'}`, the kept size rounded up to two figures in decimal GB and a currency from `navigator.language`) to that origin alone; `{stratus:'select', option}` becomes a `Choice`, and `setUpFor` maps Stratus's provider names to Keevoro's kinds (R2, S3, Google, and the S3-compatible ones as `endpoint`, with an address only if Stratus gives `endpoint`). With no `ready` in 8 seconds it says "Couldn't load the comparison just now" and offers the browser. Pages open in the browser through `open_web_page` (plain `https` only, `is_a_web_page`). The window's CSP allows `frame-src` for that one origin and nothing wider, and the frame cannot reach Keevoro's commands, which the capability gives only to the app's own window. `scripts/ui-test.mjs` serves a stand-in at that address with `page.route`, so the real site is never reached in a test.
- **What it costs, said first.** `keevoro_core::egress` is one table of what each provider charges to read data out, with the day it was checked (`CHECKED`), and `cost_said` says it in pounds with "about" in every sentence: "Reading 120 GB out of Amazon S3 costs about £9 at Amazon’s usual price; Cloudflare R2 charges nothing for this. Amazon lets each account download about 100 GB a month free, which may make it less." `the_table_of_prices_was_checked_within_a_year` fails a year after `CHECKED`, so somebody checks the prices again. `Discover::from_cloud` counts what each bucket source would be read for (once for each destination still missing the file), `destinations.room` gives it as `atAGlance.cost` (shown above Back up now, `CloudCost`), and `backup.rehearse` (`keevoro backup --dry-run`) says it.
- **Keep my folders.** A bucket's prefixes are its folders. A bucket source keeps its folders as they are when it is added (`arrange:<root>` set to `folders`), because its files carry no date of their own, only when they were put there; the person can choose by date for it as for any source.
- **AI agents.** Adding one is a change, so an agent needs changes allowed, as for adding cloud storage as a destination. The folders a person allows an agent cannot hold a bucket, so until a person can name a bucket an agent may read, `for_agents` refuses an agent's look through a bucket source and a backup that reads from one (`BUCKET_FOR_THE_PERSON`); an agent may list it.
- **Speed.** A backup of folders only pays one query of the sources table in `discover` and nothing per file; `Buckets::open` finds no bucket source and opens nothing. Looking through a bucket asks one request per thousand objects. The first screen, the survey and looking through a folder are untouched.

### What a backup looks like on disk

A backup has three folders: `originals` (the files themselves, never altered, with any other files carried along in `originals/Other files`, in the folders they came from), `renditions` (thumb, display, poster and video versions made for looking at, each named after a fingerprint of its original) and `index` (the list a gallery reads). `crates/keevoro-engine/src/layout.rs` holds the explanation of these in plain words and writes it into every backup as "What is in this backup.txt". The app shows the same on the backup screen.

Every disk a backup might go to must be able to hold a place. `keevoro_core::fit_place` leaves a place that fits alone and shortens one that does not (a name over 255 bytes, or more than 1,000 bytes in all, leaving room for a clash number under cloud storage's 1,024): each long folder name keeps its first 60 characters, then `~` and three characters of a BLAKE3 fingerprint of the whole name, the deepest folders are joined if that is not enough, and a file name keeps its ending. Case never tells two places apart, because Windows and a Mac do not: `Catalog::place_taken` compares without case (catalog step 11 adds the index for it, `collected_by_path_nocase`), and `agree_each` in `keevoro-collect` puts a new file into the spelling of a folder already used (`Catalog::folder_spelled`, asked once per folder, never per file). SQLite's `NOCASE` folds only A to Z. Places agreed before are never changed by any of this. Placing 100,000 files takes about 1.9 seconds in a debug build, against 1.4 before these checks (`how_long_placing_100_000_files_takes`, run by hand).

If you add a folder to what a backup holds, add it to `PARTS` in `layout.rs` and to the list in `ui/src/App.tsx`. A test in `send.rs` fails if a backup contains a folder the note does not explain, so this cannot be forgotten quietly.

### How a photo gets opened

Opening a photo is the slow part of making previews, and there is more than one way to do it, so the ways sit behind one small trait in `crates/keevoro-media/src/decode.rs`:

```rust
pub trait Decoder: Send + Sync {
    fn name(&self) -> &'static str;
    fn decode(&self, file: &Path, max_edge: u32) -> Result<Decoded, MediaError>;
}
```

`Decoders` holds a list of them and asks each in turn. The first one that manages it wins, so a photo the computer's codecs cannot open still gets opened by the next way down. Today the list is:

- `SystemCodecs`: the computer's own picture codecs through `keevoro_frame::photo` (WIC on Windows). Usually the fastest, hardware-assisted where the codec is, and the only way HEIC and some raw files open at all.
- `BuiltIn`: the `image` crate. Works everywhere, which is why Linux and the tests use it.
- `EmbeddedPreview`: the JPEG a camera tucks inside its raw file.

Nothing else in the workspace knows which one did the work. To add a way of decoding (ImageIO on macOS is the obvious next one), write a type that implements `Decoder` and add it to `Decoders::for_this_computer`. Nothing that calls `render_photo` has to change.

Two rules worth knowing before touching it:

- A file that cannot be read at all stops the search straight away. Trying three more decoders on a drive that has been unplugged only wastes time.
- When every way fails, the reason given is the most useful one, not the last one: "this JPEG is damaged" beats "not a kind of file I know".

The switch in Settings, Advanced ("Use this computer's own picture codecs") only decides whether `SystemCodecs` is in the list. It is on unless someone turns it off, and is kept as `plain_decoding` in the settings file so that an old settings file means "on".

Previews are made several at a time (`keevoro-collect/src/previews.rs`), on half the processor cores and never more than four, so the computer stays usable. The worker threads only decode and shrink; one thread writes to the catalog, so there is nothing to lock.

### Making previews while the originals are sent

A backup used to send every original, then make every preview, then send those. On a day-long backup that made the previews a long second wait that nobody remembered was coming. Now `keevoro-engine/src/background.rs` makes them on a thread of its own from the moment every file has its place, so they are ready, or nearly, when the originals have all arrived. It is work inside the one backup job, not a second job: the lock, the stop switch and Pause are the backup's own.

The rules, and why:

- **Originals stay first.** Previews go into the backup's own folder, as always, and are sent in a pass of their own after the originals pass (`Pass` and `uploads_for` in `send.rs`), so no preview can hold up an original. The index written after the originals lists only previews that have actually arrived. The test `the_files_themselves_are_sent_before_any_preview_is_sent` holds this.
- **A good guest.** The threads ask the operating system for low priority through `keevoro_frame::quiet` (background mode on Windows and background quality of service on macOS, both of which lower disk reads too; nice 10 on Linux). How many previews are made at once is decided every two seconds by `keevoro_core::background::preview_workers`, which is pure and tested on every platform: none on battery or while other programs use 60% or more of the processor, one while the person has touched the keyboard or mouse in the last two minutes or other programs use 25% or more, and otherwise one fewer than the foreground would use. Processor use is averaged over about ten seconds, so a spike changes nothing.
- **Kind to slow sources.** While the originals are being sent, there is never more than one preview maker per source, and the files are taken one source after another, so a USB stick or a network share is read by the sender and at most one other reader.
- **The signals that are real.** Battery and idle time on Windows (`GetSystemPowerStatus`, `GetLastInputInfo`); idle time on macOS (`CGEventSourceSecondsSinceLastEventType`); battery on Linux (`/sys/class/power_supply`); processor load everywhere, from `sysinfo`. macOS battery and Linux idle time are not known, which the rules take the careful way: unknown idleness counts as "in use", and an unknown battery is not a reason to wait.
- **Safe.** Sources are only read. A stop or a crash keeps every preview made, since each is written whole and then recorded, and the rest are made next time. A file a quick search only sampled is left until its original has been sent, because that is when its real fingerprint is learnt, and its previews are named by it.
- **After the originals.** Once they have all arrived, previews are the backup's own work again and are finished at the foreground's pace, even on battery, as they always were. If previews are switched off for a backup, none of this runs.

To test it with made-up conditions, `Previews::start_looking` takes the conditions from a closure instead of the computer.

### How long a backup has left

One estimator answers "how long until this backup is completely finished": `keevoro_core::estimate`. It is pure and is told the time, so every rule is tested with made-up clocks and rates. A running backup holds a `Tracker` (the estimator with the real clock and the count of bytes sent); the engine tells it what is happening, and `jobs.status` carries what it says as `estimate`, with how long the job has run as `runningSeconds`. The app, `keevoro status`, `keevoro follow` and `keevoro run`, and an agent's summaries all show its words, so they cannot disagree.

How it thinks:

- **A plan of stages.** `send::everywhere` gives it every stage the backup will go through before it starts (`plan` in `send.rs`): telling apart files that look alike, giving each file its place, sending the originals to each destination, making previews and video previews, sending the previews to each destination, and writing the index there. Each has an amount of work in bytes or files. What is not known yet, such as the size of previews not yet made, is estimated and then corrected as it becomes known.
- **Rates that suit the job.** A running stage's rate is measured over a window that grows with how long it has run: a third of it, between one minute and one hour. Beside it a shorter window (a sixth of the long one, between 15 seconds and 10 minutes) watches for the speed really changing. When the two differ by half again or more for as long as the short window, the long window starts again from where the change began. A stall is not adopted like that; it slides out of the long window gradually, and if nothing moves for the whole of it, the estimate says so plainly.
- **Borrowed rates.** A stage not started yet uses, in order: a rate measured for the same kind of work earlier in this backup (for sending previews, half the originals' speed to the same place), a rate remembered from earlier backups on this computer, and a cautious built-in guess (`Kind::guess`). Remembered rates are in `measured rates.json` in Keevoro's own data folder (`keevoro-api/src/rates.rs`), each moving half way towards what each backup measured. Reset forgets them.
- **Side by side.** The rest of the backup is played forward on two lanes, the sending one and the background one, and the sending of previews waits for both, so the overlap is counted rather than added up.
- **When it says something new.** The published answer is worked out again every tenth of the time left, at least every ten seconds and at most once an hour (`republish_every`): every twelve minutes on a two-hour backup, once an hour on a day-long one. It is worked out at once when a stage begins or ends, the work changes by a twentieth or more, the speed changes as above, Keevoro is let go on after a pause, or the countdown runs out before the work does. In between it counts down smoothly. Paused time does not count, for the rates or the countdown.
- **Honest wording.** Under twenty minutes it is said to the minute ("About 12 minutes left"), then to five minutes, a quarter of an hour, an hour, and "about a day". When a tenth or more of what is left rests on guesses it is said a step more roundly ("Roughly 6 hours left"); when half or more does (as at the very start of a first backup, before anything has been measured), it says "Working out how long this will take". How long it has run is measured, so it is said to the minute with no "about", by the clock since it started, saying how much was paused.

When a backup ends, everything measured is written into its history (`keevoro-engine/src/history.rs`), one entry per backup, kept in the backup's own record (the catalog's settings, as the history always was, so no change to its tables was needed). Beside the line the list shows, an entry has a `RunDetail`: when it started, how long it was paused, how it ended and who started it, Keevoro's version, each stage as the estimator recorded it (`StageRecord`: its time with pauses left out, the files or bytes it did, its average speed, and the slowest and fastest it held for a whole long window of a minute or more), what each destination's passes sent, found already there or could not send (`DestinationRecord`, filled in by `run_until` in `send.rs`), the previews made and those Keevoro could not make, the duplicates left out, and the summary exactly as it was said. The last twenty are kept in full; a destination's files that could not be sent are named up to fifty and counted beyond. Entries from before this was kept have no detail and say only what they have. `keevoro_api::words::run_in_full` says one entry in plain lines for the command line and an agent; the app draws the same from the JSON. What is not recorded, because it is not measured honestly: speeds over less than a minute, and how long each single file took.

A stage can end with a problem. When some of its files could not be sent, `run_until` in `send.rs` ends it with `Tracker::went_wrong` ("Couldn't back up 3 files") rather than `finish`; when a destination could not be reached or its turn failed part-way, `everywhere` calls `Tracker::could_not_finish_at`, which ends the stage it had got to with the reason and drops the rest of that destination's stages, so one line says what went wrong and nothing is waited for. Such a stage is `State::Problem` with its `problem` in words, said in its line, marked with a red cross in the app and "Went wrong:" for a screen reader and in text, and kept in the history's `StageRecord`.

To add a stage: add a `Kind` with its unit, its cautious guess and its label; put it in the plan in `send.rs` in the order it happens; and have the engine call `Tracker::progress` as it goes and `Tracker::finish` when it ends (or `Tracker::metered` for work counted in bytes sent). A stage done in the background beside the sending is marked by `Kind::alongside`. The screen, the command line and agents then show it with no further change.

We looked at CUDA and chose not to use it. It only works on NVIDIA cards, needs a large runtime installed, and shrinking a still photo is not where a graphics card earns its keep: reading the file and unpacking the JPEG dominate. The system codecs give most of the gain on every computer with nothing to install.

The background check for duplicates (`keevoro-api/src/jobs/duplicates.rs`) has controls of its own, because it runs after the work a person asked for and outlives a search they stopped. Its own Pause (`jobs.pause` with its `job`, `Keevoro::pause_job`) is a property of the one job, like its stop switch, never a second switch for the program: the job waits between one file and the next while it is held, and Keevoro's one Pause still pauses it with everything else; `JobStatus::paused_alone` and the activity page's `check` say which. Only the check can be paused alone. It waits on the program's Pause with `wait_while_paused_unless`, so stopping it while Keevoro is paused ends it without lifting the pause for everything else. When a person stops it (`Keevoro::stop`, or another program asking for one), the catalog setting `duplicates_stopped` notes it, and `keep_checking` (Keevoro or a backup opening) then leaves it be; the next search or backup on that backup (`Why::AfterWork`) or `duplicates.check` ("Check for duplicates now", `Why::Asked`) clears the note and starts it. Its last word then carries `stopped`, how many files are `left` and what that means (`words::check_stopped`), and `found.summary` says the same (`notChecked`, `checkStopped`). What it promises is true because `check_and_place` reads in full, before a backup sends anything, every unchecked file whose quick fingerprint is shared with another unchecked file or with one already read in full (`Catalog::checked_quick_fingerprints`), so a copy found after its original was checked is still told apart (`a_copy_found_after_its_original_was_checked_is_still_told_apart_before_a_backup`). The setting is new and optional: a catalog without it reads as not stopped, as before. In the app, `ui/src/checking.tsx` draws the line, its buttons and the stopped state, in the foot and on "What Keevoro is doing".

Keevoro should be a good guest on someone's computer. Any loop that may run for more than a moment calls `keevoro_core::pause::wait_while_paused()` once per file, so the Pause button on the Activity page reaches it, and any new kind of long job gets an entry in `src-tauri/src/activity.rs` saying what it is and why, in words a person would accept as a reason.

The app keeps a log (`src-tauri/src/log.rs`): one line per event with the time in front, in the system's usual log folder for the app, shown in Settings, Help, "What Keevoro has been doing". Log anything a person might later ask "what was it doing?" about, in the same plain words as the screens. Never log keys.

The app works in backups (see `src-tauri/src/settings.rs`): each is a named job, such as "Family photos" or "Holiday videos", with its own home folder for its catalog. In the code a backup is the job (`Backup`, `start_backup`), and sending its files to their destination is "send" (`send`, `SendPanel`, `destination`). The engine module that does the sending is `keevoro_engine::send`, shared with the command line. Within a backup there are three steps (`find`, `choose`, `backup` in `ui/src/App.tsx`; the last is shown as "Back them up somewhere safe") and the steps in the sidebar are the only navigation. The rule for any new screen: one question as the heading, one main button in the bar at the bottom, and words a person who has never heard of Keevoro would understand. The drives offered on the first step come from `keevoro-api/src/places.rs` (`places.list`), which decides what a drive is called and which system volumes to hide. They update by themselves: see [Drives that come and go](#drives-that-come-and-go). On Windows it also asks each drive letter, on a thread of its own and for at most a second and a half, whether it is a mapped network drive; the answers are kept for 30 seconds (`KEEP_FOR`) and a letter still being asked is not asked again until it answers (`Remembered`, pure and tested everywhere), since the screen asks each time it is shown and each time the window is returned to. The app's `places` command is `async`, so the asking never holds up the window.

#### Drives that come and go

The first screen updates by itself within about two seconds of a drive arriving or leaving. While its drive cards are on screen and `document.visibilityState` is `visible` (never when the window is hidden or another screen shows), it asks `places_if_changed` every two seconds (`LOOK_FOR_DRIVES_EVERY`) with the quick list it was last given. That is `places::if_changed`: it asks the system only for the drives it has mounted (`places::mounted`, `sysinfo`'s disk list with `DiskRefreshKind::nothing()`: no sizes, so never a `statvfs` on a network share that could hang; on Windows only local volumes with something in them, so a card pushed into a reader already plugged in counts), about 0.2 ms on Linux in a debug build (`the_quick_list_is_quick_and_a_look_with_nothing_changed_asks_nothing_more` prints it), and only when that differs does it make the full listing (`plugged_in`, with sizes and the mapped network drives) and say which places `arrived`. What changed is the pure `places::changed`, tested everywhere. Focus, Refresh and the system's notice list in full regardless (`asked`). On Windows `keevoro_frame::drives::on_change` (the one place this is `unsafe`) makes a hidden top-level window on its own thread that hears `WM_DEVICECHANGE` (`DBT_DEVICEARRIVAL`, `DBT_DEVICEREMOVECOMPLETE`, for a `DBT_DEVTYP_VOLUME`; a message-only window is not sent these broadcasts), and the shell turns each into the window event `drives`. On macOS and Linux the notices need Disk Arbitration's run loop or udev, much more code of that kind for no gain over a look that costs a fraction of a millisecond, so there the look alone does it. A drive that has just arrived comes first, marked "Just plugged in" with an outline that fades over 2.4 seconds (none with reduced motion), never a shade, which read as chosen. This is the first half of "run when a known source is plugged in": matching `arrived` against each backup's sources is the seam for the rest.

The web view's own right-click menu (Back, Refresh, Print) and the reload keys are off in the released app (`ui/src/noReload.ts`), since a reload drops a search or survey off the screen while it carries on; the menu stays in boxes being typed in and over selected text, and everything stays as it was in `npm run dev`.

A drive that goes while it is looked through stops the walk (`ScanReport::gone`, set by `keevoro-scan` when the place itself is no longer there), and what could not be read once it had gone is not reported as unreadable. `scan_into_with` then keeps what was found and everything found there before (`keep_all_found_before`), and the search's last word says so (`ScanEvent::unplugged`, with the drive's name from the quick list when the place is a whole drive). A backup whose source goes part-way says it once per source (`summary::source_unplugged`, from `from_sources_gone` in `send.rs`) instead of listing each file. The tests move the folder away mid-walk, which Windows refuses while the walk has it open, so they run on macOS and Linux; on Windows a real unplugging proves it.

A folder destination remembers the disk it is on (`Saved::volume`: the device number from `std::os::unix::fs::MetadataExt::dev` on macOS and Linux, and the volume's own `\\?\Volume{...}\` name from `GetVolumeNameForVolumeMountPointW` on Windows, through `keevoro_engine::reach::volume_of`), set when it is added and each time a look reaches it. A look that finds the folder on another disk with nothing of a backup in it (`confirm::on_another_disk`, pure: a folder holding a backup is the backup's whatever number its disk has today, since a drive plugged in again can be given another) is out of reach (`Looked::other_disk`), so no backup goes there, and "Check they all arrived" refuses it too (`confirm::not_on_another_disk`). The screen offers "Use this folder as it is now", which adds the folder again and so remembers its disk as it is. A destination saved before the disk was remembered has none and is looked at as before until it is next reached; the 0.37.1 fixture test checks both.

A source remembers its drive the same way (`keevoro_core::recognise::Mark`, the catalog setting `mark:<root>`, written by `looking.rs` after every look through a folder source that was not cut short: its volume, and the drive's name when the source is a whole drive). Before a source is looked through again, `recognised_at` in `keevoro-api/src/jobs/looking.rs` asks the pure `recognise`: the same volume, or none remembered (a source looked through before 0.42, or a network share), is the source; a different volume is the source only if any of up to 24 of its files (`Catalog::some_files_of`, spread through the list) are there at the same size, which is how a card the computer gives a new device number is still known. No file there means another drive: it is never looked through as the source without the person's say. `sources.look_again` passes it over with a `DifferentDrive` on the search's last word (its question in `asked`, and what happened in `said` for when nobody answers), and answers with `differentDrive`: `lookAnyway`, or `addAsNew`, which sets the source aside (`Catalog::move_source` to a place inside the backup's own `.keevoro` folder that is never made, keeping every file, choice and setting kept by its place, with `was_at` in its mark) and looks through the drive as a new source. Looking again brings a source set aside back to its place once its own drive is there, setting aside whatever source took that place meanwhile. A source that is not there at all (`is_dir` fails) is never looked through: `sources_to_look_again` passes it over with the sentence `words::not_plugged_in`, kept on the last word as `passedOver`, and refuses only when nothing is left ("None of this backup's sources are plugged in..."). `scan_into_with` in the engine refuses too, as a drive gone, when the place of a source is not a folder, so nothing that calls it can forget a source by looking at an empty place. The app's "Look again" calls `sources.look_again` (the window's `look_again`), and `ui/src/differentDrive.tsx` shows what was passed over and asks the question. `?drives=away` and `?drives=different` show both in the browser.

`ui/src/backend.ts` is the only place the screens touch the outside world. Its types mirror the Rust structs in `crates/keevoro-engine/src/discover.rs` and `src-tauri/src/events.rs`; change them together.

The shell's wiring has a test of its own, `src-tauri/src/wiring.rs`, because nobody can click through a real window in CI. It builds the app exactly as `run` does (the same plugins, commands, listener, `tauri.conf.json` and capabilities) on Tauri's stand-in for a window, `tauri::test`, with Keevoro's folders in a temporary folder. It then does what the screens do: invokes commands by the names in `backend.ts`, listens for the events `backend.ts` subscribes to, and checks every answer and every event against the types there. Along the way it surveys a made-up card, looks through it, backs it up to a folder, stops a search and a backup, and finally checks the photo arrived and the card was not touched. To make that possible, `app` in `lib.rs` takes a `tauri::Builder` for any runtime, and every command that needs the app's handle takes an `AppHandle<R>`, so a new command must too. The one step the stand-in cannot show is the page's own JavaScript receiving an event once Tauri has sent it; that is Tauri's work, and the browser test below covers the screens.

### Removing a backup

The switcher's "Manage backups…" opens `ui/src/manageBackups.tsx`. It draws the list at once from the names the app already holds, then asks for each backup's details one after another (`backup_details`, which is `backups.list` for one backup: its sources, destinations, size, last run and, in `busy`, why it cannot be changed now), so a backup with a large record never holds up the screen.

Removing is `backups.forget`, in `keevoro-api/src/removing.rs`, and is in two steps a week apart, so that a person gets the room back and nothing is left lying about, but one mis-click never loses a real backup's record:

- **At once.** With `dryRun` it only says what it would do (`Removal`, its sentences from the pure `removal_words`): the record goes, everything at each destination named stays untouched, nothing on each source named is touched, and the backup's own folder (its record, previews and working files, and how much room they take) is cleared away. Done, the backup goes from the list and its home folder is moved, in one step under the settings lock, to `removed/<id>/home` in Keevoro's data folder, with `removed/<id>/removed.json` beside it saying what it was (`Note`). If the list cannot then be saved, the folder is moved back. A home folder outside Keevoro's data folder (a library from an early version, say), judged by where it really leads as a reset judges it, is never moved or deleted, only forgotten. The background check for duplicates on it is stopped and waited for first, since it holds the record open; a search, a backup or a check on it, here or in another program, refuses the removal (and a rename) in the words other refusals use (`Jobs::working_on`).
- **A week later** (`KEPT_FOR`), when the app next starts, when `backups.removed` is asked, or at once with `backups.clear_away` ("Clear away now"), the folder set aside is deleted, and with it the keys in the keychain for cloud storage no other backup uses, listed or waiting to be put back. The keys are kept until then so that `backups.put_back` puts the backup back exactly as it was, under its own name, or with a number if another backup has taken it. Ids are never reused while one waits.

Nothing at a destination or on a source is opened by either step: `removing_a_backup_touches_nothing_at_its_sources_or_destinations_and_can_be_put_back` in `keevoro-api/src/jobs/tests.rs` backs up a card to a folder, removes, puts back, removes and clears away, and compares every file at both, byte for byte, each time. An agent can do none of this (`Agents::No`). A reset clears away what is waiting too.

### The API

Over time a good deal of what the app does was written in its shell, where the command line cannot reach it. `crates/keevoro-api` is where that logic is moving, so that the app, the `keevoro` command and, later, an AI agent's tools can all do the same things with the same words. The work is planned in steps. The first put the crate and its register in place; the second moved everything else the app's shell did, first what is quick (named backups, destinations, room, the rehearsal, pictures, settings, the log, activity, reset, the update check and what agents may do) and then the jobs. Nothing a person would notice changed. Every operation in the register is now done by the API. The third step shared jobs between programs, so a backup the app started can be watched or stopped from the command line (see [Jobs across programs](#jobs-across-programs)). The fourth rebuilt the command line on the API (see [The command line](#the-command-line)). The fifth added `keevoro mcp`, a server for an AI agent built on it (see [The server for AI agents](#the-server-for-ai-agents)).

It has six parts:

- **The register** (`src/register.rs`). One line for every operation, such as `sources.list` or `backup.run`: what it does in a plain sentence, whether it changes anything, whether it is a long-running job, whether the command line and agents get it, and whether the API does it yet. Beside the table, for each operation: whether it is about one backup (`on_a_backup`), whether a given request changes anything (`changes_with`), whether it loses something a person cannot simply put back (`loses_something`), its request as a JSON Schema made from the very type `call` reads it into (`request_schema`, with `schemars`), and the tool an agent is given for it, with its name and what it tells the agent (`tool`). Each is an exhaustive `match`, so a new operation cannot be added without saying. The command line's help and an agent's list of tools are made from all this, so write each description as carefully as a button.
- **Keevoro as a whole** (`Keevoro` in `src/keevoro.rs`). Made once from its `Folders` (config, data, cache, logs), it holds the named backups, the log and the keychain, with a method for each operation that is not about one backup. Everything is reached through `&self`, and nothing slow happens while the settings are held, so the app can keep one and ask it things from any thread.
- **Named backups** (`Backups` in `src/backups.rs`). It owns the settings file in the config folder and hands out a `Backup` by name or id. The app and the command line may both have it open, so every question is answered from the file as it is now, and every change is made under a lock (`settings.lock`, held with the operating system's file locking, so a program that stops lets go) to the file as it is at that moment, then written beside it and moved into place. One program's change never undoes another's. Which backup is "open" is the app's idea; every operation also takes a backup's name, because the command line has no open backup. `Folders::for_this_computer` says where all of this lives, the same place for every Keevoro program; a test in the app checks it is where Tauri would put an app's things.
- **A backup** (`Backup` in `src/backup.rs`, with its destinations in `src/destinations.rs`). One backup, opened by its home folder, with a method for each operation on it. Each takes and gives plain types that can be written as JSON, reusing the engine's own views where they are right.
- **Jobs** (`src/jobs/`). The long operations: looking through a source, looking again, surveying, backing up and checking, and the background check for duplicates that Keevoro starts itself after a search or a backup. Starting one returns at once with a `JobHandle` (its id, what it is, which backup, when and by whom it was started), and the job runs on its own thread, with no Tauri or Tokio needed by the caller. What it says as it goes is a `Said`, in exactly the shapes the app's screens have always received (`src/jobs/said.rs`, mirrored in `ui/src/backend.ts`). A listener can be given when a job starts, `Keevoro::listen` hears every job, and `Keevoro::follow` joins one already running; `Keevoro::jobs` (`jobs.status`) says what each running job is doing for anyone who was not listening. `stop`, `pause` and `carry_on` act between one file and the next. The rules about what may run together are here, so every front end is held to them: one search and one backup or check at a time on a backup, refused in a plain sentence, and the check for duplicates giving way to both. After a search an AI agent asked for, the check that follows reads only files in folders the agent was allowed to look in as it asked (`HowToLook::for_agent`, `deep::deep_look_where`); what it leaves waits for the next check started any other way, or for a backup. All of this works the same whichever program runs the job, as the next section explains.
- **`call`** (`src/lib.rs`). The same operations reached by name, with JSON in and JSON out, which is how the command line uses them: `call(&keevoro, op, Some("Holiday videos"), request)`. An agent's tools use `call_for_agent` (`src/for_agents.rs`) instead, which holds each call to the person's rules first and writes it to the log.

Errors are one type, `keevoro_api::Error`: the sentence the person sees, exactly as the engine wrote it, and a kind a program can act on.

Two parts need care whenever they are touched:

- **Storage keys.** They may be given to `destinations.add` and go to the keychain and nowhere else. They are held in a `Key`, whose `Debug` form is `[hidden]` and which cannot be printed or serialised; no answer carries one; an error raised while one is in hand has it taken out of its words. Keys given in a request are the ones tested and saved. Only when a request gives none are `KEEVORO_ACCESS_KEY_ID` and `KEEVORO_SECRET_ACCESS_KEY` used, and the answer (`keys`) and the log then say so, naming the variables; when backing up, the keys saved for a destination come first and the environment's only for one with none saved, said in the backup's words. The one rule is `keevoro_engine::connect::keys_to_use`, and the environment is read through `Keevoro::with_environment`, so tests give one of their own. `a_key_given_is_never_given_back_shown_logged_or_written_down` in `src/lib.rs` gives a marker key, and another pair in the environment, and searches the answer, every form of the error, other operations' answers and every file Keevoro wrote for both; `against_a_real_server_the_keys_given_are_the_ones_saved` in `connect.rs` checks what is saved, where a test server is set up.
- **What agents may do** (`src/agents.rs`). A person names the folders an agent may look through and back up to, and whether it may make changes; until they do, it may use none and only look. `AgentAccess::may_look_in` and `may_back_up_to` answer "is this path inside one of those folders?", judging a path by where it really leads and refusing on any doubt (`..`, links, the many spellings of one Windows path). Its tests attack it; add to them before changing it. `for_agents.rs` enforces it at every call an agent makes: what the person allowed is read afresh each time, operations kept for a person cannot be called, look-only operations take no request at all (so an agent can never change its own permissions), anything that changes something is refused until changes are allowed, and every folder an operation would look in or back up to (a survey's or a search's place, every source looked through again, the file behind a picture, a folder destination, each folder a backup or a check goes to) must be inside the allowed folders at that moment. What is checked is what is used: each folder the request names is replaced, before the work begins, by where it really leads (`AgentAccess::real_place_to_look_in` and `real_place_to_back_up_to`), written in its plain form and never Windows' long `\\?\` one, so a link swapped in after the check is never followed. Only a folder on that real path being swapped for a link in the moment between could still mislead it, which would need the operating system's own help to close. The backup's own sources and destinations, which the work reads from its record, are checked but not passed on. Cloud storage is not a folder; adding it is a change, so it needs changes allowed and nothing more.

To add an operation:

1. Write its tests first, against real state in a temporary folder (`keevoro::tests::keevoro` makes a `Keevoro` with a keychain in memory and no network, and `backup::tests::one_backup` a backup with photos in it). A test that runs jobs takes its turn with `jobs::tests::one_at_a_time()`, because pausing is one switch for the whole program, and waits for every job with `wait_for_jobs` before it returns. To hold a job where the test wants it, pause before starting it, or stop it from its own listener when it says the thing the test is waiting for; do not sleep and hope.
2. Add its line to the `register!` table. The `Op` enum is made from the same table, so there is no other list to remember.
3. Write the method on `Keevoro` or `Backup` and its arm in `call`. The compiler insists on the arm, and a test calls every operation to check that `implemented` tells the truth.
4. Make the app's command call it, keeping the command's name, arguments and answer exactly as `ui/src/backend.ts` expects them.

The parity test (`src-tauri/src/parity.rs`) is what stops the app drifting ahead again. It reads the app's list of commands from `generate_handler!` in `src-tauri/src/lib.rs` as it runs, and fails if any command is not on exactly one of three lists:

- `BACKED`: it only translates between the screens and register operations the API does.
- `WINDOW_ONLY`: it is about being a window, such as showing a folder or opening a web page.
- `NOT_YET`: its logic still lives in the shell. The work of moving it all to the API is done, so this is empty; it is for a command that is honestly waiting for the API.

A new button with no API operation behind it turns the build red until it is given one, or deliberately listed.

### Jobs across programs

The app, the command line and an agent's tools are separate programs, and any of them may be running when another starts a job. A person who starts a backup in the app and then types `keevoro status` expects to see it, and one who starts a backup from the command line and then presses Back up in the app expects to be told it is already happening, not to get two backups fighting over one catalog. There is no background service to referee, on purpose: it is a lot to install and keep alive for something files can do. So the programs leave notes for each other, in `crates/keevoro-api/src/jobs/across/`.

Each backup gets a small folder of its own at `jobs/<backup id>/` inside Keevoro's data folder. It is never in a source and never in a destination, and it holds three things:

- **`holder.json`, the lock.** Whichever program is doing long work on the backup (a search, a backup or a check) makes it, and removes it when the work ends. It says which process holds it, when that process started, the computer's name, the front end, and a token unique to that hold. It is made whole beside its place and linked in, which the operating system refuses if the place is taken, so two programs racing for it cannot both win.
- **`status.json`, what is happening now.** The holder writes the same `jobs.status` it gives about its own jobs as each one starts (`Across::share_now`, from `spawn`, so `keevoro status` straight afterwards finds it), a few times a second while anything changes, and every two seconds regardless. That regular write is the heartbeat. Anyone may read it without asking the holder anything, which is how `status` and `follow` see another program's job. It also keeps the last words of the last few jobs that ended, so a program waiting for one learns how it ended.
- **`requests/`, what others ask.** Another program asks the holder to stop, pause or carry on by leaving a small file here, one per request so that two askers never overwrite each other. The holder looks four times a second, does what is asked, and removes each file.

Every file is written beside its place and renamed into it in one step, so nobody ever reads half of one. Files whose names begin with a dot are these half-made ones and are never read as the real thing. On Windows something else (a virus checker, the search indexer, or another Keevoro reading it) can have a file open for a moment, and reading, moving or replacing it is then refused. Every step is tried again for up to two seconds (`files::patiently`) rather than given up on, and a request that cannot be read yet is left for the next look rather than removed unread. Giving up at once once lost a request to pause, so the other program never paused.

What a developer needs to know:

- **Only one program at a time does long work on a backup.** Within that program the old rules stand, so a search and a backup still run side by side. They are not split across two programs, because the status would then have two writers and the requests two readers, and telling a person that Keevoro is already backing up their "Family" backup from the command line, and to let that finish or stop it first, is a small price for keeping that simple. The background check for duplicates takes no lock: it gives way, within half a second, when another program starts work on its backup, and that program checks for duplicates itself when it is done.
- **`busy`, `jobs`, `follow`, `wait`, `stop`, `pause` and `carry_on` work the same whichever program runs the job.** A job in another program is marked `elsewhere` in its status. Following one hears the latest thing it said each time its status changes, not every step, and always its last word. Pausing pauses every program working on a backup, as the Pause button always paused everything. The switch (`keevoro_core::pause`) remembers whether the pause was asked for in this program or by another, without a second switch: a pause asked for here lasts until someone carries on, but one another program asked for is lifted, and said in the log, as soon as this program lets go of its last hold (`Work::nothing_held`), because from then on no other program can see its work or ask it to carry on. Otherwise the check for duplicates, which takes no lock, could sit paused where nobody else could reach it. The app asks every two seconds whether it is paused, so the foot of every screen says so, with Carry on, whoever paused it. Job numbers are unique across programs running at the same time, because each program's begin at its process number times a million.
- **The app keeps to its own jobs on screen.** Its screens hear its own jobs as events and have no way yet to follow another program's, so `send_progress` and the stop buttons only look at jobs the app is running on its open backup. Showing other programs' jobs in the app is for later. Reset is refused while any program is working.
- **A program that stops without letting go must not shut anyone out.** A lock is stale, and may be taken, when its process has gone or its number now belongs to another process (process numbers are reused, quickly on Windows; the start time tells them apart), or when its heartbeat is more than a minute old by the clock and does not move while it is watched for five seconds. That last rule catches a stuck program, and a lock written on another computer, where the process cannot be looked up. The watching is there because clocks jump: after a computer wakes from sleep, or sets its clock, a live heartbeat can look an hour old for a moment, and one that moves while watched is alive whatever the clock says. A heartbeat that seems to be in the future counts as fresh. A stale lock is moved aside in one step and checked before it is removed, and a holder checks every two seconds that the lock is still its own; if another program has taken it, it stops its work rather than share. Taking over a stale lock is written in the log.
- **Last words outlive their program for a minute.** The command line closes the moment its job ends, so the status it leaves is kept, unheld, for anyone still waiting on it. Any Keevoro program sweeps away unheld statuses more than a minute old as it lets go of a backup or closes, and removes the backup's folder once it is empty. The lock and requests are always removed when the work ends.

The timing is all in `across/lock.rs` and `across/mod.rs` as named constants: the heartbeat (`BEAT`, two seconds), when a heartbeat is doubted (`STALE_AFTER`, a minute), how long it is watched (`WATCH`, five seconds), how often the holder looks for requests (`TICK`, a quarter of a second) and how long last words are kept (`SWEEP_AFTER`, a minute). The clock and the computer's processes are behind two small traits, `Clock` and `Processes`, so the stale rules are tested with a clock the test moves and processes the test says are alive (`across/tests.rs`). Two Keevoros in one temporary folder behave as two programs, which is how most of the behaviour is tested (`jobs/tests.rs`). What only real separate processes have (their own process number, their own pause switch, and being ended without warning) is tested in `crates/keevoro-api/tests/across_programs.rs`, which runs its own test program a second time as the other program.

### Backing up by itself

A backup that runs with nobody watching (`schedule.run`, `keevoro run --unattended`) is `Keevoro::run_by_itself` in `crates/keevoro-api/src/jobs/by_itself.rs`. It is one job, an ordinary `JobKind::BackUp` to every other program (see [Words other programs read](#words-other-programs-read)), whose handle says why it started in the new field `byItself` (`keevoro_core::unattended::Occasion`) and whose `op` is `schedule.run`. It needs both slots on its backup (`Job::also_looks`), so no search starts beside it, and it holds `unattended.lock` in Keevoro's data folder, an operating-system file lock (`fs4`, as `settings.lock` is), so only one runs at a time on the computer; a second is refused as busy (`ONE_AT_A_TIME`). In order:

1. **A good moment.** The pure `keevoro_core::background::may_start` waits on battery (unless allowed), on a metered connection when the run needs the internet (a cloud destination or a bucket source; nothing yet says a connection is metered, so this never waits until one does), while other programs use `FAIRLY_BUSY` (25%) or more of the processor, and while the person used Keevoro's window in the last ten minutes (`Keevoro::note_window_used`), unless they pressed Run now. What the computer says comes through the `Signals` trait: `ThisComputer` takes five readings a second apart the first time, then one, and tests give their own (`Keevoro::with_signals`). It looks again every 30 seconds for at most `waitMinutes`, then ends "Not backed up now" with `notNow` on its last word.
2. **Looking again.** `looking::what_to_look_again`, the same rules as `sources.look_again` with nothing refused: a source not plugged in or with another drive at its place is passed over and said; a source set aside comes back if its drive has. The job's thread runs at low priority (`keevoro_frame::quiet`). Each source is looked through quickly (`looking::look_through` with `quickly`, from `keevoro_core::unattended::look_quickly`): the catalog's own record of the last look (`Catalog::found_at`, each file with when it last changed, catalog step 16, `items.modified`, in nanoseconds as its listing said) becomes a `keevoro_scan::Known`, and the walk hands a file whose size and modified time are both exactly as then, of the same sort (photo or video, or another file asked for) and with a fingerprint as full as wanted, straight to the results as it was found, never opening it. Everything else is read as ever, and a file found by a version that kept no time is read and given one. Every file is read again 30 days after the last full look (`FULL_LOOK_EVERY`; `full_look:<root>` in the catalog's settings, written by every look that was not quick and was neither stopped nor cut short, so a person's Look again counts), and a time more than a day ahead counts as never. `save_scan` keeps the quick fingerprint a file was known by beside the whole one it is taken with, so a later sampling search still recognises it. Only a run by itself looks quickly; Look again pressed by a person reads every file. The tests are `looking_again_quickly` in `keevoro-scan/src/tests.rs` (a file changed inside with its size and time put back is not opened; a size, time or new file is; a time not kept, a quick fingerprint where a whole one is wanted, and a kind switched off since are not trusted) and `a_backup_by_itself_looks_again_quickly_and_reads_every_file_again_once_a_month` in `jobs/tests.rs`.
3. **What waits.** The pure `keevoro_core::unattended::what_waits` from facts gathered by `Run::facts`: never asked how to arrange it, or reading from bucket sources costing about £1 or more (`UNATTENDED_COST_LIMIT`, from `egress::estimated_pounds`, the careful way, and only asked when there is a bucket source, so a folder-only backup pays nothing for it), holds the whole run back and sends nothing; new pictures set aside, new copies (sent once, as always) and another drive at a source's place are listed. The owner chose to send newly found copies once and list them rather than hold them.
4. **Sending.** `backing_up::send_and_record`, shared with `backup.run`, with `HowToSend { unattended: true }`: the engine does not send to a destination whose look found it emptied or replaced (`Looked::emptied`; one on another disk is out of reach for every backup already), and says so (`send::NOT_SENT_THERE`); a few files gone are still sent again. A backup never asked how to arrange it is never settled to "by date" when unattended.
5. **Saying it.** The last word carries `heldBack` (what waits, a sentence each), the history entry carries `RunDetail::by_itself` (why, what was looked through and passed over, what was new, what waits), and the command line's exit code is 6 when something waits and 7 when it did not run now. History keeps such a run even when it sent nothing, when something was passed over or waits.
6. **Afterwards.** The check for duplicates starts with `Why::AfterRunningByItself`: low priority, and it gives way while the computer is on battery or busy (asked every 30 seconds), to carry on next time Keevoro opens.

The tests are in `jobs/tests.rs` (`a_backup_run_by_itself_holds_back_what_needs_the_persons_say_and_sends_the_rest`, `one_backup_runs_by_itself_at_a_time_and_none_starts_on_battery`), the engine's `confirm/tests.rs`, `keevoro-core`'s `unattended.rs` and `background.rs`, and the command line's `a_backup_run_by_itself_for_a_system_scheduler_says_in_its_exit_code_what_happened`.

### Backing up on a schedule

The rules are pure, in `keevoro_core::schedule` (with `jiff`, which bundles the time zones on Windows, already in the tree through other crates): `slot_on`, `next_slot_after`, `latest_slot_at_or_before`, `due`, `handled_after_run`, `accounts_for_its_slot` and the words (`every_words`, `next_words`, `catching_up_words`). Each is given the time zone and the moment, never reads the clock, and is tested in `schedule/tests.rs` with zones written as POSIX strings (London, New York, Sydney, and Havana, whose clocks change at midnight), so the tests need no time-zone files: a time the clocks skip is moved on by the gap (01:30 on the spring morning in London runs at 02:30), a time that happens twice runs once, the 31st is the last day of a shorter month, forty days off is one run, saving or carrying on never runs at once, a run longer than its period does not start again, a clock that once said 2030 does not stop every run, and no run comes within half a period of the last (a journey west, or Run now an hour before).

Each backup keeps its schedule in its own catalog's settings (`crates/keevoro-api/src/schedule.rs`): `schedule`, the person's choice, written only by `schedule.set`, and `schedule_state` (`Record`: what is accounted for, the slot to skip, when it last ran, whether a run is going, and the last ten attempts, including those that found nothing new, which the history does not keep). A choice this version cannot read counts as none and is kept as `schedule_unreadable` before anything is written over it. Nothing for this is in `settings.json`. The time and time zone are read at the edges only, through the `Clock` trait (`SystemClock`, read each time so a change of time zone counts at once; tests move their own with `Keevoro::with_clock`).

`Keevoro::run_schedules_due` is the scheduler's look: for each backup, its schedule and record are read from its catalog at most every 15 minutes or when changed here (`Known`), and a backup whose slot is due starts `run_by_itself_if_due`, which decides again under the computer-wide lock, so the app and a system scheduler calling `keevoro run --unattended --if-due` never both run it. A slot skipped, or too soon after the last run, is accounted for and said in the last few with no run. One found busy is tried again in 15 minutes. A run marks `running_since` as it starts and clears it as it ends, so one cut short when Keevoro closed or the computer shut down is said by the next ("This run carries on from where it was"), and its slot, never accounted for, is caught up once. The app starts a thread in `setup` (`src-tauri/src/lib.rs`) that looks once a minute at what is in memory (`Ticker`, pure: nothing in the first five minutes after opening or waking, so a person who has just sat down is not met by a backup); the window tells Keevoro, at most once a minute, that it is being used (`window_used`, `useNoteWindowUse` in `ui/src/schedule.tsx`), and a run by itself waits ten minutes after that. When the window is closed, a run that ends with something worth saying is told with a system notice (see [Running with the window closed](#running-with-the-window-closed)); the card and the history update when a run ends. With twenty backups each on a schedule, the first look read every catalog in about 17 ms and each look after that took about 0.08 ms in a debug build (`how_long_a_look_at_twenty_schedules_takes`, run by hand); opening a screen, looking through a source and a backup a person starts do none of this.

**When a source is plugged in.** "Back up when this is plugged in" is `sources.on_arrival` (`crates/keevoro-api/src/arrival.rs`), kept in the backup's catalog as `arrival:<root>` = `go` (`keevoro_core::arrival::key`; anything else is off), shown on each source as `onArrival` (`discover`), and refused for a bucket source. The app's thread `keevoro arrivals` (`src-tauri/src/lib.rs`) calls `Keevoro::notice_arrivals` every three seconds: it reads the sources with the choice on from every catalog at most once a minute (at once after a change here), asks `reach::is_there` of each, and gives each place to the pure `keevoro_core::arrival::Watch`: plugged in means not there and then there (a card in when Keevoro starts is left alone), it must stay `SETTLE` (10) seconds, at most one run in `AT_MOST_EVERY` (ten minutes), nothing while paused (a card still in on carrying on is backed up then), and another backup running is tried again in `BUSY_RETRY` (a minute). It then checks the drive is the source (`jobs::there_as_itself`, the same rule as looking again: a different drive at its place is never backed up) and starts `run_by_itself_for_source`, which looks through that source alone (`Run::only`) and waits up to an hour for a good moment. The app says so with a notice (`notices::plugged_in`) and the run's own notice as it ends. The new reason, `Occasion::SourceArrived`, is written in the shared job files as `runNow` with `pluggedIn` beside it (`shared_occasion`), since 0.42 to 0.48 cannot read a word they do not know and would take the job's lock for garbled; `a_backup_started_by_its_source_being_plugged_in_is_read_by_a_0_42_program_as_run_now` proves it. An agent cannot change the choice (`Agents::No`).

**While you were away** is `schedule.away` (`Keevoro::away`, pure in `schedule::away_of`): for every backup whose catalog can be opened, its attempts since a time (each with `when_words`, "Yesterday at 02:31", and `caught_up_words` from `Attempt::missed`, the slots before it that `due` counted as missed, kept in `schedule_state` only when not zero, so a record from before reads as catching up nothing), a slot due more than ten minutes ago that has not run yet (`MISSED_AFTER`), and the newest attempt held back for the person's say. The app asks with `since` from `Desk::away_since`, which is when the window was last seen as it comes back from being closed or hidden, and Done (`away_seen`) moves it to now; the command line's `keevoro away` and an agent's `while_you_were_away` ask for the last week (`days`). The panel is `ui/src/away.tsx`, at the top of the backup screen; `?byitself&away` in the browser shows it. `Record::note` keeps a run that waited again for the same reason as the one before as one line, moving its time on, so a laptop on battery all night does not fill the last few.

The card is `ui/src/schedule.tsx`, on the backup screen above "How earlier backups went": the schedule and when next in Keevoro's own words, Change, Pause or Carry on, Skip the next one (Don't skip it), the last few runs with a word for each (never colour alone), and Run now (`run_scheduled_now`, which is `run_by_itself` with `Occasion::RunNow`). "Set it up…" opens the dialog: only when I press Back up, every day, week or month, at a time in 15-minute steps, with what a run does in plain words. `?schedule` in the browser shows one set with its last few. Settings, Backing up by itself, shows the same schedule and opens the same dialog (`ScheduleDialog`). An AI agent may read a schedule (`backup_schedule`) but not set, skip or pause one, or start a run by itself: the owner's choice.

### Running with the window closed

Keevoro can keep running by the clock while its window is closed, so backups by themselves happen on time. It is the app's own business (`src-tauri/src`), with the deciding done in pure functions:

- **What closing, minimising and quitting do** is `closing.rs`: `on_close`, `hides_on_minimise`, `on_quit`, and `keeps_running`, which is the person's choice or else on where the icon is surely shown (Windows, a Mac) and off on Linux, where GNOME shows no tray without an extension. With it on, closing hides the window; the first time, the window says so first (`Close::SayFirst`, the dialog in `ui/src/tray.tsx`: "Keevoro will keep running by the clock so your backups happen on time.", where the icon is, "Start Keevoro when this computer starts" never ticked for the person, and "Quit Keevoro instead"). With it off, closing quits as it always did. Quitting with a backup, a check or a search in hand asks first, in the window brought forward ("A backup is running. Stop it after the file in hand and quit? Nothing is lost."), and stops it with `stop_here_and_wait`. Minimising is ordinary unless "Minimise to the icon by the clock" is on.
- **Where the choices are kept** is `window.json` in Keevoro's config folder (`keevoro_api::window`), never `settings.json` (see [When what Keevoro keeps changes](#when-what-keevoro-keeps-changes)): `keepRunning` (absent until the person chooses), `minimiseToTray`, `explainedClose`, `notify` and `seenAt`. Settings shows them in Backing up by itself, under "When the window is closed" and "Notifications" (`ui/src/settings/backingUp.tsx`). Reset removes the file and the app takes its entry for starting with the computer away.
- **Hiding destroys the window**, webview and all, and `RunEvent::ExitRequested` is prevented while it was hidden on purpose (`window.rs`); bringing it back makes it again from `tauri.conf.json`, whose window is `"create": false` so that a start with the computer opens none. Measured on Linux under Xvfb with the debug build: about 380 MB with the window shown (the app 125 MB, WebKit's web process 230 MB, its network process 26 MB) and about 180 MB hidden (the web process gone). Bringing it back from a second start took under 100 ms to the window and about as long as opening Keevoro to the page. While hidden, Keevoro's measuring of its own work rests (`activity::rest`), so nothing wakes more often than the scheduler's once a minute, and the icon's thread sleeps until something changes. Whether WebView2's helper processes go on Windows must be measured there.
- **What the window is told** as it comes forward (a page, the first-close explanation, the question before quitting, a note from the icon's menu) waits in `window::Ask` until the page takes it with `window_ask`, nudged by the `window_ask` event; a window just made is not listening yet, so it asks as it starts.
- **The icon by the clock** is `tray.rs`. Its menu is one pure function, `tray::menu`, from `Keevoro::at_a_glance` (`keevoro_api::glance`, pure words in `glance::said`): a line that cannot be clicked saying what is happening ("All backed up. Next: tonight at 02:30", "Backing up Family photos, about 12 minutes left", "Paused", "Something needs your say"), Open Keevoro, Pause (for an hour, until tomorrow morning, until I carry on) or Carry on, Back up now (each backup by name when there are several; an ordinary backup, `backup.run`, as the window's button starts), Stop this backup while one runs, Settings… and Quit Keevoro. The tooltip is the same line. Pausing is Keevoro's one Pause, so the window and the icon agree; a pause for a while ends by itself at the scheduler's next look (`carry_on_if_the_pause_is_over`) and the window's foot says until when. "Something needs your say" follows a run by itself that held something back, could not reach a destination, was refused or missed files, since the window was last open (`seenAt`). A click on the icon brings the window back on Windows; on a Mac a click opens the menu, as menu-bar items do; Linux's tray only ever opens the menu. The icon shows the mood in its shape: the logo alone when calm, and a badge with an arrow, two bars or an exclamation mark, made from the logo by `cargo xtask tray-icons` into `src-tauri/icons/tray/` (in colour at 32 pixels, and black and clear at 44 for the Mac's menu bar), checked by `cargo xtask tray-icons --check` and `cargo test`. It keeps itself up to date when nudged: by every job event, a pause, the window coming and going and the scheduler's minute; it looks at most every two seconds, and every five while something is going. Where the tray library is missing (Linux without libayatana-appindicator3), making the icon fails, Keevoro says so in the log and behaves as it always did.
- **One Keevoro window program at a time**: `tauri-plugin-single-instance`, registered first in `run()`, so starting Keevoro again brings this one forward. The command line and the agent server are other programs and never ask.
- **Starting with the computer** is `tauri-plugin-autostart` behind `startup::StartWithComputer`, with `--in-background` (`closing::IN_BACKGROUND`): off until the person ticks it, under the name Keevoro, with no administrator rights (Windows: the `Run` value in the current user's registry, shown in Task Manager's Startup apps; a Mac: a Launch Agent; Linux: `~/.config/autostart`). The system's entry is the truth; Keevoro keeps no copy. Tauri's uninstaller removes the `Run` value when not updating, and `src-tauri/windows/hooks.nsh` removes Task Manager's note beside it; an update keeps both, and installs to the same place, so the entry stays right.
- **Updates** never cut a run short (`updates::may_install`). On Windows the installer reopens Keevoro (`/R`) with its window, which is where Update was pressed. On a Mac, where the new app is dragged over the old one while it runs, Keevoro compares its bundle's version on disk with its own once a minute, and with nothing in hand opens the new one (hidden if its window was) and goes (`relaunch.rs`).

- **Notices** are `notices.rs`, through `tauri-plugin-notification` from Rust only: when a backup by itself ends, the pure `notice` decides from its last word whether there is something worth saying (files sent, something waiting for the person's say, a destination out of reach, a run refused, files missed) and says it in the run's own sentences; nothing new, a stop, or waiting for a better moment says nothing, and nothing is shown while the window is in front of the person. "Tell me when a backup by itself finishes" in Settings, Backing up by itself, turns them off. A click brings the window back on the backup screen (`page: send`), opened on that backup when no window was open; the plugin reports clicks on Windows while the notice is on screen and on a Mac.

The tests are `closing.rs`, `tray.rs`, `window.rs` and `notices.rs` (pure), `keevoro-api`'s `glance.rs` and `window.rs`, `updating.rs`, the wiring test (the choices, starting with the computer through a list in memory, what waits for the window, and quitting with a search in hand asking first) and the browser test (`?closing`, `?quitting&busy`, and Settings). Tauri's stand-in for a window has no tray, no system list of programs to start and no notifications, so those are proved on real computers only.

### Reporting a problem or an idea

Settings, Help, "Report a problem or suggest an idea" (and the same page from the foot of the window) and `keevoro report` send a person's words to a private list only Keevoro's maker reads. Four operations do it, none of them offered to an AI agent, since a report is the person's own: `reports.prepare` makes the report as the exact text that will be sent (pure, in `keevoro_core::report`), `reports.send` checks that text is still a report Keevoro made, with a scrubbed log, and sends it as it is, so what the person was shown is byte for byte what goes; `reports.list` reads what is kept on this computer, and `reports.refresh` asks after each one. By default a report holds the kind, the words, Keevoro's version, the operating system and the screen. The end of the log goes only with "Include the end of Keevoro's log" on, scrubbed first (`report::scrub`: the home folder and user name become `~`, anything shaped like a key, a secret or a token becomes `•••`), and cut from the front to 120 KB so the newest lines survive.

The address is built in with `KEEVORO_REPORTS_URL` at compile time, or else the usual one, and the same variable at run time overrides it: the tests point it at a stand-in on this computer (`reports/tests.rs`, the command line's tests and `updating.rs`), and the browser test uses the stand-in backend, so no test reaches the real service. It uses `ureq`, as the updater does, with the computer's own certificates and a 15 second wait, always off the window's thread.

### Words other programs read

`holder.json` and `status.json` (see [Jobs across programs](#jobs-across-programs)) are read by every Keevoro program on the computer, including older ones: an older `keevoro` command beside a newer app, or a release rolled back. An older program that meets a word it does not know there cannot read the file at all, and a lock it cannot read counts as garbled, which it takes over once it is a minute old; so a new variant would let an old program start a second backup on the same catalog. So `FrontEnd`, `JobKind` and `Outcome` never gain a variant. Anything new about a job (that it was started by a schedule, that something waits for the person) is a new field marked `#[serde(default, skip_serializing_if = ...)]`, which older programs pass over. `the_words_older_programs_read_in_shared_files_never_grow` in `jobs/across/tests.rs` fails to build when a variant is added, so whoever adds one reads this first.

### The command line

`crates/keevoro-cli` is the `keevoro` command, and it is translation only: every command turns what was typed into one operation in the register, calls it through `keevoro_api::call`, and says the answer in plain English, or prints it exactly as the API gave it with `--json`. It works on the same named backups as the app because it opens Keevoro in the same folders (`Folders::for_this_computer`), or under `KEEVORO_HOME` when that is set.

- `src/commands.rs` has one row for each command as it is typed (`keevoro backups start`): its words, the operations it can call, its arguments, how it makes the request and how it shows the answer. Its help is the register's own sentence, and a command for a job gets `--detach` because the register says it is one. `every_operation_the_register_offers_the_command_line_has_a_command` in `src/tests.rs` fails if an operation marked for the command line has no row, the command line's own parity test.
- `src/show.rs` says each answer, from the API's JSON.
- `src/jobs.rs` runs a job and follows it to its end, with progress on one rewritten line when a person is watching and a plain line for each new step otherwise. `follow` hears a job in any program. `--detach` starts the same command again as a program of its own (`KEEVORO_DETACHED_JOB` tells it so), which says on its first line how the job started and then runs it with nobody listening.
- `src/keys.rs` takes storage keys from standard input, the environment, the command or the keyboard, straight into the request. `a_key_given_is_never_shown_logged_or_written_down` gives a marker key every way and searches everything the program said and wrote for it; `tests/the_program.rs` does the same through the real program.

The exit codes are in `Code` in `src/main.rs`, made from the API's error `Kind` and, for a backup or a check, from the `outcome` of its last word, so a script need never read a sentence. They are listed for people in [docs/command-line.md](command-line.md#for-scripts).

To add an operation for the command line, add its row; the test above tells you if you forget. The tests in `src/tests.rs` run commands in the test program itself, with a keychain in memory and no network (`At::keevoro`); those that run jobs take their turn with `one_at_a_time()`, because pausing is one switch for the whole program. What only a real separate program shows (its exit code, `--detach`) is in `tests/the_program.rs`.

### The server for AI agents

`crates/keevoro-mcp` is `keevoro mcp`, a Model Context Protocol server over standard input and output, in the same program as the command line (`keevoro-cli` hands over to it). It uses `rmcp`, the official Rust SDK, with only its `server` and `transport-io` features: nothing that opens a network connection. Like the command line it is translation only, and it holds no rules of its own:

- `src/tools.rs` makes each tool from the register: name, description, input schema (the request's schema, with `backup` added for an operation about one backup, and nothing at all for a look-only one), and the protocol's hints: `readOnlyHint` for an operation that changes nothing, and `destructiveHint` for one that `loses_something`. Its tests fail if an operation offered to agents has no tool, or a tool has no operation offered to agents: the agents' parity test.
- `src/lib.rs` is the server. Each `tools/call` runs on a thread of its own, goes through `keevoro_api::call_for_agent`, and answers with a summary in plain English and the API's own JSON (as `structuredContent` too, when it is an object); a picture comes back as an image. A problem is a tool result with `isError`, the API's sentence and its kind; only a tool that does not exist is a protocol error. Keevoro's log is a resource, `keevoro://log`, read through `read_for_agent`.
- `src/said.rs` writes the summaries.

A job answers at once with its handle; `job_status` (`jobs.status`) follows it, and with `waitSeconds` waits up to 30 seconds (`LONGEST_WAIT`) for it to end. Asked about one job by its id once it has ended, `jobs.status` answers how it ended, with its last word (`ended` is true), whichever program ran it. There are no progress notifications: polling is enough, and works the same for a job the app started.

Standard output carries the protocol and nothing else, so nothing in Keevoro may print. The command line no longer locks standard input and output for the whole run, because the server reads and writes them from threads of its own. A panic in the server is written to Keevoro's log. When the AI app closes its side, the server asks its own jobs to stop after the file in hand (`stop_here_and_wait`, which leaves other programs' jobs alone), waits up to a minute, and ends.

`src/tests.rs` speaks to the server over a pipe in memory. `crates/keevoro-cli/tests/mcp.rs` starts the real `keevoro mcp` and speaks to it over its standard input and output, through a whole first backup with a person allowing each step from the command line beside it; it also gives a marker key and searches every answer, standard error, the log and Keevoro's folders for it, checks that every line of standard output is the protocol and that standard error is empty, and checks the agent and the command line take turns on one backup.

### Tests that need a server

The S3 adapter is tested against a real S3-compatible server. CI starts MinIO for this. Locally those tests skip themselves unless you point them at a server; the variables are listed at the top of `crates/keevoro-storage-s3/src/tests.rs`.

## When what Keevoro keeps changes

People keep Keevoro for years and update it without thinking about it, and from now on some of them are not us. So the rule is simple: **nothing a person has set or backed up, and nothing Keevoro has recorded for them, may be lost by an update.** Version 0.39.0 broke it. It changed how "what this backup is for" was written down, from one word (`"photos"`) to a list (`["photos"]`), without converting what was already there, so anyone who had chosen photos only or videos only quietly got everything again. Nobody noticed, because until then the only user was the person writing the code.

What Keevoro keeps, and where:

| What | Where | Holds |
| --- | --- | --- |
| The settings file | `settings.json` in Keevoro's config folder (`keevoro-api/src/backups.rs`) | The backups and which is open, the codecs switch, what AI agents may do, the kinds of file changed |
| Each backup's catalog | `.keevoro/catalog.sqlite` in the backup's home (`keevoro-catalog`) | What was found, every keep or skip, places, what reached each destination (and, from 0.43, when each copy was last proved by reading it back, `proved_at`), and the backup's settings: destinations, what it is for, folders and endings left out, previews, history, what the last backup said, and the drive each source was last looked through on (`mark:<root>`, from 0.42) |
| Remembered speeds | `measured rates.json` in Keevoro's data folder (`keevoro-api/src/rates.rs`) | How fast earlier backups went, for the next estimate |
| The window's choices | `window.json` in Keevoro's config folder (`keevoro-api/src/window.rs`, from 0.45) | Whether closing keeps Keevoro running, minimising to the tray, whether the first-close explanation was said, notices, and when the window was last open. New, so no older version rewrites it; read a part at a time and kept aside when damaged |
| Reports sent | `reports.json` in Keevoro's config folder (`keevoro-api/src/reports.rs`, from 0.46) | Each report of a problem or an idea sent from this computer: its reference, the token that asks after it, its first line and what was last heard of it. New, so no older version rewrites it; read a report at a time, changed under `reports.lock`, and kept aside when damaged |
| Removed backups | `removed/<id>/` in Keevoro's data folder (`keevoro-api/src/removing.rs`) | A removed backup's own folder and a note of what it was, for a week, to put back |
| Caches | Keevoro's cache folder | Previews, remembered maps (`surveys/`) and `look.sqlite`. These may be thrown away and made again, but must be made again quietly, never fail |

When you change any of these:

1. **Write a conversion.** For the catalog, add a step to `MIGRATIONS` in `keevoro-catalog` (never edit an old one): step 10 turns the old one-word choices into lists. For a JSON form, read the old form as well as the new, or give a new field a default that means what an older file meant.
2. **Read each part on its own.** One part that cannot be understood must cost that part alone. The settings file is read a part at a time (`Settings::from_value`), and a file that could not all be understood is kept beside it as `settings that could not be read.json` before anything is written over it. The history is read an entry at a time, and entries this version cannot read are kept as they were.
3. **Add to the fixture.** `crates/keevoro-api/tests/fixtures/0.37.1/` holds a settings file, two catalogs and the remembered speeds exactly as 0.37.1, the version our first outside tester had, wrote them, and `crates/keevoro-api/tests/updating.rs` opens them with today's Keevoro and checks everything a person would notice. When you change a stored form, put an example of the old form in the fixture (the catalogs are plain SQL, made from that version's own schema steps, with places in braces filled in by the test) and a line in the test that it reads as it did. When a release has changed a form, add a folder for that version beside `0.37.1` rather than editing the old one: the old fixture stays as proof that people on that version can still update.
4. **Say it in the changelog** if anything a person had set needed converting, and how it was put right.

**The settings file is the hardest place to add anything.** Older versions read it a part at a time and write back only the parts they know, so a part a newer version adds is lost the first time an older one (an older `keevoro` command, or a release rolled back) changes a setting. Since 0.42 `Settings` keeps the parts it does not know (`later`) and writes them back, so this version and later ones no longer drop them, but older ones still do. Put anything new in a backup's catalog (whose settings table older versions leave alone) or in a file of its own that no older version writes. `nothing_new_goes_in_the_settings_file_without_knowing_older_versions_drop_it` in `backups.rs` fails to build when a part is added, so whoever adds one reads this first. Nothing for backing up by itself goes in `settings.json`.

## Cutting a release

The work of a release is done before it, in [CHANGELOG.md](../CHANGELOG.md). Every change a person would notice goes under **Unreleased** as it lands, in one of **Added**, **Changed**, **Fixed** or **Removed**, written for the person using Keevoro: what they will see, not which function moved. Those notes become the GitHub Release, and a release refuses to run while the section is empty.

The headings also decide the version number:

| Unreleased lists | The release is | From 0.2.1 |
| --- | --- | --- |
| Something **Added** or **Removed** | A minor release: something a person would notice as new, or gone | 0.3.0 |
| Only **Changed** and **Fixed** | A patch | 0.2.2 |

That is the whole rule. It lives in `next_version` in `crates/xtask/src/changelog.rs` and is covered by `cargo test`. It follows that the heading a change is filed under matters: a new ability belongs under Added even when it is small, and a rework of something that already exists belongs under Changed. You can always overrule it by giving a number yourself, which is how 1.0.0 will happen. Whatever the number, it must be higher than the last, because installed copies only ever move to a higher version.

### The button

On GitHub, open **Actions**, pick **Release** on the left, press **Run workflow**, and press the green button. Leave the version blank and the changelog decides it; type one to choose yourself. The run's page says which number it took and why. Only people with write access to the repository can do this. The workflow then:

1. Works out the version if none was given, and refuses if it is not higher than the last release, if CI has not passed on the latest commit to main, or if the changelog has nothing under Unreleased.
2. Dates the Unreleased section as the version and opens a fresh one, sets the version in `Cargo.toml`, updates `Cargo.lock`, commits and tags.
3. Creates the GitHub Release as a draft, with the changelog section as the notes.
4. Builds the command-line program for Windows (x64), macOS (one file for Apple silicon and Intel) and Linux (x64), checks each build reports the right version, and uploads them to the draft.
5. Builds the desktop app's installers for Windows and macOS with `scripts/build-installer.sh`, the same script CI uses, and uploads them too.
6. Adds a `SHA256SUMS` file and publishes the release, so "latest" never points at a release with nothing to download.

Day to day, steps 4 and 5 build for **Windows only**. GitHub's macOS machines are often slow to come by, and during fast development they held releases up for hours. For a milestone, tick **all platforms** and the release is built for macOS and Linux as well. The same goes for CI: every change is tested on Windows and on Linux (in the coverage job), and macOS is tested when the CI workflow is run by hand with **all platforms** ticked. Do that before a milestone release, since a Windows-only release says nothing about the Mac.

A Windows-only release has no Mac or Linux files on it. The Mac app only offers an update when the release has a Mac installer, so Mac users are simply not offered it.

Tick **Rehearse** to see steps 1 and 2 in the log without anything being pushed, built or published. It is also the way to ask what number the next release would be. A rehearsal can run from any branch.

The moment the workflow finishes, the one-line installers and `keevoro update` pick up the new version.

### The terminal

```sh
cargo xtask release
```

```sh
git push --follow-tags
```

If the release commit reaches main but the tag does not (some environments may push commits but not tags), finish it from the button: run **Release** and type that version. The workflow sees the version is already cut, tags it and builds.

The first command fetches the tags, works out the number the same way and says which it chose; `cargo xtask release 0.3.0` chooses for it. It is exactly what the button runs, so the two routes cannot drift. The tag push starts the Release workflow at the build step. The terminal route does not check CI for you.

`cargo xtask` is the project's own tooling, in `crates/xtask`. It is written in Rust so it behaves the same on every platform with nothing else to install. `cargo xtask` on its own lists what it can do.

## Rolling back a release

If a release turns out to be broken, open **Actions**, pick **Roll back**, press **Run workflow**, give the last good version and one sentence on why. The workflow then:

1. Marks every release newer than the good one as a pre-release, which withdraws it. GitHub's "latest" points at the good version again at once, so the installers hand out the good version and `keevoro update` no longer offers the bad one.
2. Puts the good version's code back on main as one commit, **Roll back to vX**, with a line in the changelog saying so and why. The release tooling (`.github`, `.cargo`, `crates/xtask`, the install scripts and `CHANGELOG.md`) keeps its current state.
3. Releases that code as the next patch number, higher than the withdrawn release, so copies that already took the bad version move to the good code the next time they update.

Step 3 is why a rollback is a release and not a deletion. The updater compares version numbers and only ever installs a higher one, so the only way to move a copy off 0.3.0 is to give it a 0.3.1. Anyone who wants an older build by hand can still download it from the releases page; the withdrawn ones stay there, marked pre-release.

Work on main that landed after the good version is no longer on main afterwards. It is not lost: bring it back with `git revert` of the Roll back commit, fix what was wrong, and release again.

## How installing and updating work

Each release carries the command-line program for three systems, the desktop app's installers for two, and a checksum file:

| File | For |
| --- | --- |
| `keevoro-windows-x64.exe` | Windows 10 and 11 |
| `keevoro-macos-universal` | macOS, Apple silicon and Intel |
| `keevoro-linux-x64` | Linux on x86_64 |
| `Keevoro-windows-x64-setup.exe` | The desktop app's Windows installer (per-user, no administrator) |
| `Keevoro-macos-universal.dmg` | The desktop app for macOS, Apple silicon and Intel |
| `SHA256SUMS` | Checking any of the above arrived intact |

The names carry no version, so "the latest Windows build" is always the same address.

`install.sh` and `install.ps1` at the repository root ask GitHub for the latest release, download the right file, check it against `SHA256SUMS`, and put it in the user's own programs folder (`~/.local/bin`, or `%LOCALAPPDATA%\Programs\Keevoro` on Windows, which is also added to the user's PATH). Neither needs an administrator. Running an installer again updates.

`keevoro update` does the same from inside the program (`crates/keevoro-update`): it asks for the latest release, and if that is a higher version it downloads the build for this computer, checks it, and swaps itself for it in one step. `keevoro update --check` only reports. This, sending a report, and showing the comparison of cloud storage (Stratus) are the only times Keevoro contacts the internet without being given a storage address, and each happens only when asked; there is no background check, in keeping with "nothing leaves the machine without consent".

### If the repository is made private

The repository is public, so none of this needs a login. If it is ever made private again, GitHub stops showing its releases to strangers, and the installers and `keevoro update` need a token: a fine-grained personal access token with read-only **Contents** access to this one repository, in `GITHUB_TOKEN` (or `KEEVORO_GITHUB_TOKEN` if `GITHUB_TOKEN` is taken). The install scripts would then be fetched through `https://api.github.com/repos/markcastle/keevoro/contents/install.sh` with that token and the header `Accept: application/vnd.github.raw`.

Being public also matters for cost: GitHub Actions is free and unlimited for public repositories, but metered for private ones, where a macOS minute counts as ten.

### What is not signed yet

The checksum proves a download arrived intact. It does not prove who made it, because the checksum file comes from the same place as the program. Two things would add that, and both need something only the owner can provide:

| What | Needs | Gives |
| --- | --- | --- |
| Windows code signing | An Authenticode certificate, as repository secrets | No SmartScreen warning on first run |
| Apple Developer ID and notarisation | An Apple Developer account (99 USD a year), as repository secrets | No Gatekeeper warning; today the build has only a free ad-hoc signature |

Until then the install scripts clear the first-run warnings, as they are run by someone who has chosen to trust the repository. The desktop app (phase 3) will use Tauri's updater, which signs every update with a key of our own, the way Task Rail does.
